# 안 본 작품 스킵 — 설계 문서

작성일: 2026-07-30
전제 문서: [`2026-07-29-story-compass-design.md`](./2026-07-29-story-compass-design.md)

## 1. 무엇을 고치는가

사용자가 안 본 작품이 페어로 나오면 선택할 수 없다. 지금은 빠져나갈 길이 없어서 이탈하거나 아무거나 누른다.

문제는 두 갈래다.

1. **둘 다 안 봤다** — 못 고른다. 이탈하거나 무작위로 눌러서 채점에 노이즈가 들어간다.
2. **한쪽만 봤다** — 아는 쪽을 고른다. **친숙도가 축 선호로 위장돼 점수에 들어간다.** 사용자 눈에는 안 보이면서 결과 품질만 조용히 깎는 쪽이라 1번보다 위험하다.

지금 구조가 이걸 만드는 이유는 명확하다. `lib/selector.ts`의 `bestPair`는 `2 * gap - confound`만 최대화하고 **작품이 얼마나 알려졌는지는 목표 함수에 아예 없다.** `data/works.json`에 인기도 필드도 없다. 그래서 「트라이앵글」(2009)이 「어벤져스」와 동등한 확률로 나온다.

**설계 원칙: 안 본 작품은 고르게 하지 않는다.** 포스터와 제목의 느낌으로 고르게 유도하는 대안도 검토했으나 채택하지 않았다. 그 선택은 친숙도 편향을 노이즈로 바꿀 뿐이고, 축 라벨은 작품의 주제적 입장이라 줄거리를 모르면 대응하는 신호가 없다.

### 비목표

인기도 가중, 사전 캘리브레이션 설문, 스킵 이력의 세션 간 저장(localStorage), 스킵 횟수 상한, 문항 조기 종료. 근거는 5절과 6절에 있다.

## 2. 동작

각 포스터에 개별 **"몰라요"** 버튼을 둔다. 누르면 **그 작품만** 세션에서 영구 제외되고, 상대편 작품은 다음 페어에 재등장할 수 있다.

작품 단위인 이유는 페어 단위("둘 다 안 봤어요")보다 정보 효율이 두 배이기 때문이다. 페어 단위는 아는 작품까지 같이 버려서, 한쪽만 몰라도 스킵하는 사용자가 풀을 두 배로 소모한다. 작품 단위는 한쪽만 몰라도 스킵하는 사용법을 감당할 수 있게 만들고, 그래서 1절의 2번 편향까지 잡는다.

스킵은 **라운드를 소모하지 않는다.** 문항 수는 12개 고정을 유지한다 (전제 문서 3절: 고정 길이여야 진행률 바를 정직하게 그릴 수 있고, 완주율이 성공 기준이다).

진행률 바는 라운드 기준을 그대로 쓴다. 스킵해도 움직이지 않는 것이 정직하다. 별도의 "제외한 작품 N개" 카운터는 넣지 않는다.

문구는 원칙을 명시적으로 드러내는 쪽으로 바꾼다. 플레이 헤드를 `더 끌리는 쪽을 고르세요` → `본 작품 중 더 끌리는 쪽을 고르세요`로 하고, 안 본 작품은 몰라요를 누르라고 안내한다.

## 3. 코드 변경

### `lib/selector.ts`

`nextPair(pool, choices, seed, excluded)` — `excluded: ReadonlySet<number>`를 받아 `used` 초기값에 합집합으로 넣는다.

**반환 타입을 `Pair | null`로 바꾼다.** 지금은 후보가 없을 때 `no available pair`를 throw하고 `app/play/page.tsx`가 잡지 않아서 퀴즈 중간에 화면이 죽는다. 두 실패를 구분한다.

- **풀 자체가 작다** (`pool.length < ROUNDS * 2`) — 설정 버그이고 사용자가 도달할 수 없다. 계속 `throw`한다.
- **제외가 쌓여 후보가 말랐다** — 사용자가 도달 가능한 정상 상태다. `null`을 반환하고 UI가 처리한다.

`MIN_GAPS = [3, 2, 0]` 폴백은 그대로 둔다.

`excluded`는 **필수 인자**로 둔다. 기본값을 준 선택 인자로 만들면 프로덕션 호출 지점이 빠뜨려도 컴파일이 통과해 스킵이 조용히 무력화된다. 프로덕션 호출 지점은 `app/play/page.tsx` 한 곳뿐이므로 필수로 두는 비용이 낮다.

### `app/play/page.tsx`

`excluded` 상태(`Set<number>`)를 추가한다. 갱신은 새 `Set`을 만들어 대입한다 — 기존 `Set`을 변형하면 React가 리렌더를 건너뛴다.

`pair === null`이면 막다른 길 화면을 띄운다: "아는 작품이 너무 적어 진단을 완성할 수 없어요" + 다시 시작. 조기 채점은 하지 않는다 (전제 문서의 비목표).

### `components/PosterCard.tsx`

`onSkip` prop을 추가한다. 포스터 탭은 선택, 몰라요는 제외다.

현재 루트 요소가 `<button>`이라 그 안에 버튼을 중첩할 수 없다 (HTML 위반이고 클릭 이벤트가 겹친다). 루트를 `<div>`로 바꾸고 선택 영역과 몰라요를 형제 `<button>` 둘로 나눈다. 포스터 로드 실패 시 제목만 보여주는 기존 폴백은 유지한다.

### 안 건드리는 것

`lib/payload.ts`, `lib/scoring.ts`, 공유 URL 포맷, `data/works.json`, `lib/pool-health.ts`.

`score()`는 `choices`만 쓰고 페이로드는 최종 12쌍만 담으므로 **스킵은 순수 세션 로컬 상태다.** 페이로드 포맷도 공유 링크도 안 건드리고, 그래서 전제 문서 6절의 인덱스 안정성 리스크가 0이다.

## 4. 테스트

### 기존 테스트 이관

`nextPair` 호출 지점이 `lib/selector.test.ts` 6곳과 `lib/works-pool.test.ts` 1곳에 있고, 반환 타입이 `Pair | null`이 되면 `pair.left` 접근이 전부 타입 에러가 된다. 각 지점에 `!`를 흩뿌리지 말고 테스트 헬퍼를 하나 둔다.

```ts
function mustPair(pool: Work[], choices: Choice[], seed: number, excluded = new Set<number>()): Pair {
  const pair = nextPair(pool, choices, seed, excluded)
  if (pair === null) throw new Error('nextPair returned null')
  return pair
}
```

`null`이 나오면 그 자리에서 실패하므로, 기존 단정문의 의미가 그대로 유지되면서 회귀를 놓치지 않는다. 기존 실제 풀 회귀 테스트(`gap >= 3`, `confound <= 2`)는 `excluded`가 빈 집합일 때 그대로 통과해야 한다.

### 추가할 테스트

- `excluded`에 든 작품은 반환 페어의 `left`/`right`에 절대 나타나지 않는다
- 후보가 마르면 `null`을 반환한다 (throw하지 않는다) — `mustPair`가 아니라 `nextPair`를 직접 호출해 검증한다
- 스킵을 반복해도 `choices`가 늘지 않는다 — 즉 라운드를 소모하지 않는다
- 풀이 `ROUNDS * 2`보다 작으면 여전히 throw한다 (기존 동작 회귀)

## 5. 검증한 것

실제 240개 풀로 시뮬레이션했다 (조건별 200회, 사용자가 풀의 일정 비율을 안다고 가정).

| 아는 비율 | 둘 다 모를 때만 스킵 | 하나라도 모르면 스킵 |
|---|---|---|
| 50% | 완주 100%, 중위 16쌍 | 완주 100%, 중위 37쌍 |
| 30% | 완주 100%, 중위 23쌍 | 완주 100%, 중위 69쌍 |
| 20% | 완주 100%, 중위 33쌍 | 완주 100%, 중위 100쌍 |
| 10% | 완주 100%, 중위 62쌍 | **완주 52%**, 중위 150쌍 |

세 가지가 나왔다.

- **풀 고갈은 거의 안 일어난다.** 240개 중 24개만 쓰니 여유가 크다. 유일한 실패 조합이 "풀의 10%만 알면서 하나라도 모를 때마다 스킵"이고, 그게 3절의 `null` 처리가 반드시 필요한 이유다.
- **진짜 병목은 고갈이 아니라 탭 횟수다.** 스킵 버튼은 문제를 해결하는 게 아니라 일부 구간에서 사용자 노동으로 옮긴다.
- **스킵 횟수 상한은 넣지 않는다.** 상한 40~120은 모두 완주율 100%를 만들지만, 상한의 유일한 가치가 "도달 후 느낌으로 골라 완주시키기"였고 1절 원칙이 그 탈출구를 막았다. 원칙을 유지하면 상한은 안전장치가 아니라 막다른 길 제조기가 된다 — 상한 40에서는 풀의 30%를 아는 사용자의 상한 도달률이 100%라서 전원이 막다른 길에 빠진다. 상한을 없애는 쪽이 더 많은 사용자를 완주시킨다.

## 6. 인기도 가중을 빼는 근거

`bestPair`에 `+ w * fame`을 더해 유명작을 우선 노출하면 스킵 자체가 줄어든다. 검토했고 v1에서 뺐다.

**TMDB에 쓸 만한 fame 프록시가 없다.** 풀 240개의 실측값을 받아 확인했다.

- `popularity`는 해외 작품에서 `voteCount`와 순위상관 **rho = -0.312**다. 상위가 「로 앤 오더」·「NCIS」·「수퍼내추럴」 같은 롱런 시리즈이고 하위에 「셔터 아일랜드」·「디파티드」·「듄: 파트 2」가 앉는다. 최근 페이지 조회 트래픽 지표라서 인지도와 무관하고, 그대로 가중치로 쓰면 **오히려 무명작을 우선 노출한다.**
- `voteCount`를 쓰면 한국 작품이 밀려난다. 전체 voteCount 순위에서 한국 작품 116개의 중위값이 **182위/240**이고 상위 50위 안에 **2개**뿐이다. TMDB 투표자가 서구권이라 당연한 결과이나, 한국 사용자 친숙도로는 거꾸로다. `scripts/build-pool.ts`가 `MIN_KOREAN_RATIO = 0.3`으로 확보한 한국 작품 비중이 선택 단계에서 무력화된다.

쓰려면 한국 작품과 해외 작품을 각각 그룹 내 백분위로 정규화해야 하는데, 그 프록시가 실제로 한국 사용자의 친숙도 순서를 만드는지는 별도 검증이 필요하다. v1 스코프에서 뺀다.

**감수하는 비용을 명시해둔다.** 인기도가 없으면 선택기는 계속 유명세를 보지 않으므로, 5절 표의 20~30% 구간(69~100쌍)이 그대로 남는다. 풀은 한국 작품 116개에 마블·해리포터·픽사가 섞인 구성이고, 한국 사용자의 현실적인 인지 비율 중위값을 40~50%로 본다. 그 구간은 16~26쌍으로 끝나므로 v1은 스킵만으로 충분하다고 판단한다.

**재검토 조건:** 스킵 로그의 실제 분포가 저커버리지 쪽으로 치우치면 인기도 가중을 다시 꺼낸다. 그때 `data/works.json`의 기존 240개에 `fame` 필드를 제자리 덮어쓰기로 추가하면 되고, `selectPool`을 재실행할 필요가 없어 전제 문서 6절의 인덱스 안정성이 유지된다.
