# Story Compass — 설계 문서

작성일: 2026-07-29
코드네임: `story-compass` (최종 브랜딩·서비스명 결정은 이 스펙의 범위 밖)

## 1. 무엇을 만드는가

영화·드라마 두 편을 놓고 고르는 일을 12번 반복하면, 그 선택들로부터 사용자의 **서사 정체성 유형**을 네 글자 코드로 판정해 한 장짜리 결과 카드를 보여주는 웹 서비스.

성공 기준은 정확도가 아니라 **공유율과 완주율**이다. 이 서비스는 바이럴 놀이이며, 결과 카드가 캡처되어 카카오톡·인스타그램으로 퍼지는 것이 유일한 목표다. 설계상의 모든 트레이드오프는 이 기준으로 판정한다.

### 비목표 (명시적으로 만들지 않는 것)

로그인, 사용자 계정, 데이터베이스, 결과 저장, 유형별 통계·분포, 음악 등 영상 외 콘텐츠, 다국어, 우승작을 뽑는 결승 라운드, 문항 조기 종료. 이들은 v1에 넣지 않는다.

## 2. 성향 축

축은 "이 사람이 어떤 이야기의 주인공인가"를 묻는 **서사 정체성축** 네 개다. 작품의 주제로 직접 라벨링할 수 있어 근거가 탄탄하면서, 결과 문장이 개인적으로 읽힌다.

| 축 | 양극 | 글자 |
|---|---|---|
| 1 | 세계를 바꾼다 ↔ 세계를 견딘다 | `C` (Change) / `E` (Endure) |
| 2 | 답을 찾는다 ↔ 질문 속에 산다 | `A` (Answer) / `Q` (Question) |
| 3 | 함께 간다 ↔ 혼자 간다 | `T` (Together) / `S` (Solo) |
| 4 | 이겨서 얻는다 ↔ 잃으며 깨닫는다 | `W` (Win) / `L` (Lose) |

네 글자를 축 순서대로 이어 붙이면 `EQSL`, `CATW` 같은 코드가 되고 총 16유형이다. 본문은 한국어지만 코드는 알파벳으로 두어 공유 시 그대로 쓰이게 한다.

각 작품은 네 축 각각에 대해 **-2에서 +2 사이의 정수** 점수를 갖는다. 음수가 첫 번째 글자(C/A/T/W) 방향, 양수가 두 번째 글자(E/Q/S/L) 방향이다. 5단계 정수를 쓰는 이유는 LLM 라벨링의 일관성이 연속값보다 높고, 축 격리 조건을 정수 비교로 단순하게 검사할 수 있기 때문이다.

## 3. 적응형 페어 선택

이것이 이 서비스의 핵심 알고리즘이다.

토너먼트 브라켓을 쓰지 않는 이유는 브라켓이 **우승자를 뽑는 데 최적화된 구조**이기 때문이다. 라운드가 진행될수록 생존 작품이 한쪽 취향으로 쏠려서 후반 매치는 새 정보를 거의 주지 못한다. 16강 15매치 중 실제로 성향을 판별하는 건 초반 절반뿐이다.

대신 매 라운드 시스템이 다음 쌍을 직접 고른다. 선택 규칙:

1. **목표 축을 정한다.** 지금까지 수집한 정보량이 가장 적은 축을 고른다. 축 `a`의 정보량은 `info[a] = Σ |W[a] - L[a]|` (지금까지 보여준 모든 쌍에 대한 합)이다. 동점이면 **세션 시드로 셔플한 축 순서에서 앞선 축**을 쓴다. 첫 라운드는 네 축이 모두 0이므로 항상 이 규칙을 타며, 그래서 세션마다 다른 축에서 시작해 첫 문항이 매번 달라진다.
2. **후보 쌍을 평가한다.** 아직 등장하지 않은 작품들로 만들 수 있는 모든 쌍 `(x, y)`에 대해:
   - `gap = |x[t] - y[t]|` (목표 축 `t`에서의 차이)
   - `confound = Σ|x[a] - y[a]|` (목표 축을 **제외한** 나머지 세 축의 차이 합)
   - `score = 2 × gap − confound`
   - `gap >= 3`이 아닌 쌍은 후보에서 제외한다.
3. **최고점 쌍을 고른다.** 동점일 때는 세션 시드로 결정론적으로 셔플한 순서에서 첫 번째를 쓴다. 같은 시드는 항상 같은 대진을 만든다.

**`confound` 항이 이 알고리즘의 전부다.** 한 쌍이 네 축 모두에서 크게 갈리면 사용자가 왜 그것을 골랐는지 해석할 수 없다. 목표 축에서만 벌어지고 나머지 축에서는 붙어 있는 쌍만 내보내기 때문에, 12번의 선택이 낭비 없이 네 축에 꽂힌다.

한 작품은 세션당 최대 한 번만 등장한다.

**후보가 비는 경우.** 7절의 풀 검증을 통과했다면 12라운드 안에 후보가 고갈될 일은 사실상 없지만, 동작은 정의돼 있어야 한다. 목표 축에서 `gap >= 3`인 쌍이 하나도 없으면 그 다음으로 정보량이 적은 축으로 넘어간다. 네 축 모두에서 없으면 `gap >= 2`로 완화해 같은 절차를 반복한다. 그래도 없으면 남은 작품 중 `score`가 가장 높은 쌍을 그냥 쓴다.

문항 수는 **12개 고정**이다. 적응형이므로 축이 일찍 수렴하면 조기 종료도 가능하지만, 끝이 안 보이면 이탈한다. 고정 길이여야 진행률 바를 정직하게 그릴 수 있고, 완주율이 성공 기준이므로 진행률 바가 조기 종료보다 가치가 크다.

풀 240개 기준 후보 쌍은 약 2.9만 개이며, 매 라운드 전수 평가해도 브라우저에서 즉시 끝난다. 인덱스나 사전계산은 필요 없다.

## 4. 점수 계산과 유형 판정

12라운드가 끝나면 각 라운드의 승자 `W`와 패자 `L`에 대해 **네 축 모두를** 갱신한다.

```
theta[a] = Σ (W[a] - L[a])
denom[a] = Σ |W[a] - L[a]|
norm[a]  = theta[a] / max(denom[a], 1)     // -1 .. +1
```

목표 축만 갱신하지 않고 네 축을 모두 갱신하는 이유는, 선택기가 이미 `confound`를 최소화했으므로 비목표 축의 기여가 자연히 작기 때문이다. 특수 처리 없이 같은 식을 쓰는 편이 단순하고 정직하다.

- 글자 결정: `norm[a] < 0`이면 첫 번째 글자(C/A/T/W), `norm[a] >= 0`이면 두 번째 글자(E/Q/S/L). 정확히 0인 경우가 두 번째 글자로 가는 것은 임의적이지만 결정론적이어야 하므로 이 규칙으로 고정한다.
- 막대그래프 길이: `|norm[a]| × 100%`.

**상극 유형**은 네 글자를 모두 뒤집은 코드, **잘 맞는 유형**은 축 3(함께↔혼자)만 같고 나머지가 뒤집힌 코드로 정의한다. 규칙으로 정의하므로 16유형에 대한 별도 매핑 테이블이 필요 없다.

## 5. 결과 카드

우승작이 없으므로 시각적 무게는 다음이 진다.

- 네 글자 코드와 유형 이름 (가장 크게)
- 3~4줄 유형 설명
- 네 축 막대그래프
- **"당신이 고른 12편" 포스터 스트립** — TMDB 포스터를 깔아 화면을 채우고, 사용자가 자기 선택을 되짚어보게 해 체류를 늘린다
- 상극 유형 / 잘 맞는 유형
- 다시 하기, 공유 버튼

**OG 이미지가 실제 확산 엔진이다.** `@vercel/og`로 코드와 유형 이름을 큼직하게 박은 이미지를 동적 생성한다. 이게 없으면 링크가 회색 박스로 뜨고, 결과가 아무리 좋아도 퍼지지 않는다.

## 6. 아키텍처

Next.js (App Router) + Tailwind, Vercel 배포, **데이터베이스 없음**.

```
scripts/build-pool.ts     TMDB 후보 수집 → LLM 라벨링 → data/works.json 생성 및 검증
data/works.json           작품 풀 (커밋 대상)
data/types.ts             16유형 이름과 문안
lib/selector.ts           적응형 페어 선택 (순수 함수)
lib/scoring.ts            선택 기록 → 축 점수 → 유형 코드 (순수 함수)
lib/payload.ts            선택 기록 URL 인코딩/디코딩
app/page.tsx              랜딩
app/play/page.tsx         12라운드 진행 (클라이언트 상태)
app/r/[code]/page.tsx     결과 카드
app/r/[code]/opengraph-image.tsx   OG 이미지 동적 생성
```

`selector.ts`, `scoring.ts`, `payload.ts`는 전부 순수 함수이며 React나 Next에 의존하지 않는다. 이 세 파일이 서비스의 로직 전부이고, 단독으로 테스트된다. 나머지는 표현 계층이다.

`build-pool.ts`는 **수동 실행 스크립트**다. CI에 걸지 않고, 결과물인 `works.json`을 커밋한다. 그래서 런타임에는 TMDB API도 LLM API도 호출하지 않는다.

### 작품 데이터 스키마

```ts
type Work = {
  id: number                              // TMDB id
  media: 'movie' | 'tv'
  title: string                           // 한국어 제목
  year: number
  poster: string                          // TMDB poster_path
  axes: [number, number, number, number]  // 각 -2..+2, [CE, AQ, TS, WL]
  labeledAt: string                       // ISO 날짜, 6개월 갱신 주기 관리용
}
```

### 공유 URL

결과 URL은 `/r/<code>?p=<payload>` 형태다. `payload`는 12쌍의 (승자, 패자) 작품 인덱스를 바이트 배열로 담아 base64url로 인코딩한 것이다. 풀이 240개이므로 인덱스는 1바이트에 들어가고, 24바이트 → 32자로 URL에 무리 없이 실린다.

코드가 경로에 있는 이유는 URL 자체가 읽히고, OG 이미지 생성이 payload를 디코드하지 않고도 동작하기 때문이다. 결과 페이지는 payload로 코드를 재계산해서 경로의 코드와 다르면 올바른 코드 URL로 리다이렉트한다.

서버 저장이 없으므로 운영 부담이 0이다.

**작품 인덱스는 고정이다.** payload가 담는 것은 TMDB id가 아니라 `works.json`의 배열 인덱스다. 따라서 10절의 6개월 갱신에서 **배열 순서를 바꾸거나 중간 항목을 제거하면 이미 공유된 링크가 조용히 다른 작품을 가리킨다.** 링크가 깨지는 게 아니라 그럴듯한 오답으로 바뀌기 때문에 아무도 눈치채지 못한다.

갱신 규칙을 이렇게 고정한다.

- 기존 항목의 `title`·`poster`·`year`는 **제자리에서 덮어쓴다.** 순서를 바꾸지 않는다.
- 작품 추가는 **배열 끝에만** 한다.
- TMDB에서 사라진 작품은 제거하지 않고 자리를 유지한다. 선택기에서 빼야 한다면 축 점수를 모두 0으로 만들어 격리 쌍 후보에서 자연히 탈락시킨다.

id를 직접 담아 인덱스 의존을 없애는 방법도 있지만, 풀에서 빠진 작품은 어차피 복원할 수 없으므로 링크 수명은 나아지지 않고 payload만 네 배로 길어진다. 순서 고정이 더 단순하고 효과가 같다.

## 7. 작품 풀 구축

**후보 수집.** TMDB `/discover`로 movie와 tv 각각 `vote_count >= 1000` 인기순 상위를 긁고, 별도로 `original_language=ko` 작품을 확보한다. 한국 사용자가 제목을 보고 아는 작품이어야 선택이 성립하므로, 한국 작품 비중을 최소 30%로 잡는다. 연도도 분산시켜 특정 시기에 몰리지 않게 한다. 후보 400개를 모아 최종 240개를 선별한다.

**라벨링.** LLM에 **제목, 연도, 매체 종류만** 전달하고 네 축 점수를 받는다. TMDB의 줄거리·장르·태그는 넣지 않는다. 두 가지 이유가 있다. 첫째, TMDB 약관은 TMDB 콘텐츠로 AI를 학습시키는 것을 금지하는데, 추론과 학습은 다르지만 애초에 넣지 않으면 이 조항을 건드릴 일이 없다. 둘째, 축이 작품의 **주제적 입장**에 관한 것이라 줄거리 요약보다 모델이 이미 아는 작품 지식이 더 정확하다.

라벨링 결과는 사람이 스팟체크한다. 특히 각 축의 극단(-2, +2)에 배치된 작품은 전수 확인한다. 극단값이 선택기의 `gap >= 3` 조건을 만족시키는 주력이라 여기가 틀리면 전체가 흔들린다.

**풀 검증.** `build-pool.ts`는 생성 후 다음을 검사하고, 하나라도 실패하면 리포트를 출력하고 0이 아닌 코드로 종료한다.

- 네 축 각각에 대해, 음수 극단(-2, -1)과 양수 극단(+1, +2)에 각각 최소 40개 작품이 있을 것
- 네 축 각각에 대해, `gap >= 3`이고 `confound <= 2`인 사용 가능한 쌍이 최소 200개 있을 것
- 모든 작품이 유효한 `poster` 경로를 가질 것
- 중복 TMDB id가 없을 것

두 번째 조건이 가장 중요하다. 풀이 크기만 하고 축 조합이 편중되면 선택기가 격리된 쌍을 못 찾아 조용히 `confound`가 높은 쌍을 내보내기 시작한다. 이건 겉으로 드러나지 않고 결과 품질만 갉아먹으므로, 빌드 시점에 잡아야 한다.

## 8. 오류 처리

런타임에 외부 API 호출이 없으므로 실패 지점이 거의 없다. 남는 것은 세 가지다.

- **TMDB CDN 포스터 로드 실패** — 제목만 크게 적은 텍스트 카드로 폴백한다. 이미지 하나 때문에 진행이 멈추면 안 된다.
- **payload 디코드 실패 또는 길이 불일치** — 랜딩으로 리다이렉트한다.
- **payload는 유효한데 경로의 코드와 재계산 코드가 불일치** — payload를 신뢰하고 올바른 코드 URL로 리다이렉트한다.

## 9. 테스트

순수 함수 세 개가 로직 전부이므로 테스트도 거기 집중한다.

- `scoring`: 알려진 선택 시퀀스가 기대한 코드를 내는지
- `scoring`: 모든 gap이 0인 퇴화 입력에서도 결정론적으로 코드가 나오는지
- `selector`: 같은 작품을 두 번 내보내지 않는지
- `selector`: 반환하는 모든 쌍이 목표 축에서 `gap >= 3`인지
- `selector`: 12라운드 후 네 축 모두 `info[a] > 0`인지
- `payload`: 인코딩 후 디코딩이 원본과 같은지, 손상된 입력에서 예외 없이 실패를 반환하는지
- 데이터 무결성: 16개 코드 전부에 유형 이름과 문안이 존재하는지, `works.json`이 7절의 검증을 통과하는지

## 10. TMDB 약관 준수

TMDB API는 비상업 사용에 한해 무료다. 다음을 지킨다.

- 광고를 붙이지 않고 비상업으로 운영한다. 수익화하려면 별도 상업 계약이 필요하다.
- 푸터에 TMDB 로고와 "This product uses the TMDB API but is not endorsed or certified by TMDB." 고지를 넣는다. TMDB 로고는 서비스 자체 로고보다 작게 배치한다.
- `works.json`은 6개월 주기로 갱신한다. `labeledAt` 필드로 만료 작품을 찾는다. TMDB 데이터 캐시 상한이 6개월이다.
- LLM에는 TMDB 콘텐츠를 전달하지 않는다 (7절 참조).
