# 밸런스 검증 보고서

`npm run sim`으로 실제 게임 코드를 렌더링 없이 돌려 얻은 결과다.
브라우저와 **완전히 같은 `Game` 클래스를 같은 1/60초 고정 타임스텝**으로 굴리므로,
여기 나온 수치는 추정이 아니라 실제 플레이의 수치다.

**현재 판**: 스테이지 6 · 기물 8종 · 적 20종 · 대조군 전략 20종.
6스테이지 × 20전략 × 20판 = **2,400판, 약 100초**.

---

## 1. 검증 방법

### 시뮬레이터 구성

```
src/sim/
├─ coverage.ts    건설 가능 타일을 "경로를 얼마나 오래 사정권에 두는가"로 순위 매김 (사거리별)
├─ strategies.ts  빌드 방침만 다르게 둔 대조군 AI들
├─ headless.ts    한 판을 끝까지 돌려 결과 레코드를 뽑는다
└─ run.ts         스테이지 × 전략 × 시드를 돌리고 집계·감사 표를 출력
```

핵심은 **대조 실험**이다. 배치 알고리즘·판단 주기·업그레이드 규칙을 전부 동일하게 고정하고
**"어떤 타워를 짓는가" 하나만** 바꾼다. 그래야 클리어율 차이를 빌드 탓으로 돌릴 수 있다.

**스테이지마다 그 시점에 해금된 타워만 준다.** 이게 진행 설계의 검증 그 자체다 —
S2를 총통 없이 못 깬다면 S1의 보상이 제 역할을 한다는 뜻이고, 있으나 없으나 같다면
그 해금은 허울이다.

- 시드는 `0x1000 + i × 7919`로 고정 — 같은 명령이면 항상 같은 결과가 나온다
- 전략은 결정적(난수 없음) — 결과 차이는 오직 스폰 지터 시드에서만 온다
- 판단 주기 0.5초, 준비 단계에서 살 수 있는 것을 다 살 때까지 골드를 소진
- 해금되지 않은 타워를 고르면 쓸 수 있는 것 중 가장 싼 것으로 대체한다

### 명령

```bash
npm run sim                      # 전체 스테이지 × 전체 전략 × 20판
npm run sim -- --stage fork      # 특정 스테이지만
npm run sim -- --runs 50         # 시드 수 지정
npm run sim -- --only balanced,adaptive-frost1
npm run sim -- --markdown        # 이 문서에 붙일 표 형태로 출력
npm run sim -- --audit           # 스테이지별 압박·수입 곡선 (시뮬레이션 없이 데이터만)
npm run sim -- --income 1.3      # 수입 전역 배율 스윕 (튜닝용, 데이터는 건드리지 않음)
npm run sim -- --hp 0.8          # 적 HP 전역 배율 스윕 (튜닝용)
```

`--income`과 `--hp`는 밸런스의 양쪽 축이다. 데이터를 손으로 여러 번 고쳐가며 재는 대신
배율로 스윕해 목표 구간을 찾은 뒤, 확정된 값만 데이터 파일에 반영한다.

### 시뮬레이터의 한계 (결과를 읽을 때 감안할 것)

- **자리 평가는 사거리별로 한다.** 예전에는 평균 사거리(3.2칸) 하나로 순위를 매겨 모든
  기물에 돌려썼는데, 사거리 1.9의 살수를 넣자 곧바로 깨졌다 — 3.2칸 기준 1위 자리는
  경로에서 떨어져 긴 구간을 얕게 덮는 곳이라 **1.9칸으로는 경로에 아예 닿지 않는다.**
  살수 몰빵이 방어 0인 첫 판에서도 2웨이브에 죽은 게 그 증거였다(기물 셋을 짓고 아무것도
  못 죽였다). 지금은 사거리별로 다시 매겨 캐시한다. 기고는 경로를 덮을 필요가 없으므로
  **이미 깔린 기물이 가장 많이 들어오는 자리**를 따로 고른다.
- **AI는 최적 플레이가 아니다.** 배치는 커버리지 순위 상위부터 채우고, 웨이브 중 대응이 없고,
  타워를 팔지 않고, **자리를 다시 잡지 않는다**. 사람이 더 잘할 수도, 더 못할 수도 있다.
- **AI가 결정적이라 임계값 근처에서 비단조적 결과가 나온다.** 클리어율은 절대값보다
  전략 간 상대 비교로 읽어야 한다.
- **배치 규칙이 틀리면 밸런스가 아니라 배치를 재게 된다.** 8장에 그 실례가 있다 —
  거마작을 여러 판에 걸쳐 "지을수록 진다"고 재고 있었는데, 원인은 수치가 아니라
  자리를 잘못 잡는 규칙이었다.
- **타겟팅 우선순위는 전부 기본값(선두)** — 이 축은 여전히 검증하지 않았다.

## 2. 검증이 잡아낸 버그

**패배 판정이 조용히 취소되던 문제** (`src/game/Game.ts`)

"거마작 몰빵" 전략이 **생명 0으로 20웨이브를 클리어**하는 결과가 나왔다. 있을 수 없는 조합이라
추적해 보니, 웨이브의 마지막 적이 유출되며 생명이 0이 된 직후 같은 프레임의
`checkWaveCompletion()`이 `phase`를 `'prep'`으로 덮어쓰고 있었다. 승리·패배를 종착 상태로
못 박는 `setPhase()` 가드로 수정했다.

**중독 피해가 타워 기여도에 잡히지 않던 문제**

비격진천뢰의 딜 점유율이 4%로 나왔는데, 지속 피해가 `Enemy.update`에서 적용되어 쏜 타워에
귀속되지 않고 있었다. 지표만의 문제였지만 그대로 뒀다면 "비격진천뢰는 쓸모없다"는 잘못된 결론으로
이어졌을 것이다. 귀속을 고치니 10%로 올라갔다.

## 3. 지나온 두 번의 붕괴 (요약)

**(1) 스테이지 도입 이전** — 첫 검증에서 11개 전략 중 10개가 100% 클리어, 대부분 무손실이었다.
원인은 경제였다: 이론상 수입 11,462G인데 타워 14기 만렙 비용은 4,500G. 골드가 남아도니
상성 페널티가 타워 개수로 상쇄됐다. 수입 −39%, 궁수대 정체성 복원(L3 36 → 24),
적 방어 상향으로 몰빵 0% / 조합 87~100%까지 잡았다.

**(2) 스테이지 도입 직후** — 골드가 스테이지마다 0부터 시작하는데 웨이브는 "20웨이브 내내
누적한다"는 전제로 쓰여 있어 S2~S5가 전부 초반 전멸했다. 여기서 나온 가장 중요한 발견:

> **경로가 갈라지면 난이도가 급격히 올라간다.**
> 타워 커버리지가 경로 수만큼 나뉘기 때문이다. 다중 경로 맵은 압박을 **절반 이하로**
> 낮춰야 같은 체감 난이도가 된다.

그래서 웨이브를 스테이지마다 **목표 HP 곡선**(`base × ramp^(웨이브-1)`, 마지막만 ×1.6)에서
다시 생성하고, 확정된 값을 `src/data/stages.ts`에 명시적으로 박아 뒀다.
자세한 경위는 이 문서의 이전 판(git 히스토리) 참고.

## 5. 검증 결과 (각 스테이지 × 20전략 × 20판)

전체 표는 `npm run sim -- --runs 20 --markdown`으로 재생성할 수 있다.
아래는 각 스테이지에서 **설계 의도를 판정하는 행만** 뽑은 것이다.

한눈에 보는 요약 — **몰빵은 S3부터 전부 막히고, 조합은 스테이지마다 최소 하나가 100%다.**

| 스테이지 | 몰빵 최대 | 균형(3종) | +거마작 | +살수 | +기고 |
|---|---|---|---|---|---|
| S1 왜구의 노략 | 100% (튜토리얼) | 100%/20.0 | 100%/20.0 | 100%/20.0 | 100%/20.0 |
| S2 삼포왜란 | **총통 100%** (그 판의 교훈) | 100%/14.2 | 100%/12.9 | 100%/11.8 | 100%/12.6 |
| S3 니탕개의 난 | **0%** | 35%/0.7 | **70%**/1.6 | 5%/0.1 | 55%/1.4 |
| S4 임진왜란 | **0%** | 95%/5.5 | 100%/**13.9** | 100%/6.0 | 100%/**14.4** |
| S5 정묘호란 | **0%** | 55%/1.4 | **100%**/7.7 | 100%/8.6 | 100%/6.4 |
| S6 병자호란 | 포수 5% | 100%/4.0 | 100%/**10.0** | 100%/6.5 | 100%/**18.0** |

`클리어율/남은 생명`. 「+X」는 `균형(3종)`과 같은 순환에 X를 하나 더한 것이라,
둘의 차이가 곧 그 기물의 값이다.

**세 서포터가 각자 다른 판에서 값을 한다.** 거마작은 기마가 몰리는 S3·S4·S5
(35% → 70%, 5.5 → 13.9, 55% → 100%), 기고는 기물이 많이 깔리는 S4·S6
(5.5 → 14.4, 4.0 → 18.0), 살수는 맨몸 물량이 나오는 S5(1.4 → 8.6). **살수가 S3에서 35% → 5%로 오히려 해가 되는 것도 설계대로다** —
니탕개의 난은 별동대(산개 65%)와 갑병이 주역이라 백병이 양쪽에 다 깎인다.

### S1 왜구의 노략 — 8웨이브 · 사수·살수

거의 모든 전략이 **100% 클리어, 생명 20/20**. **살수 몰빵만 생명 16.2**로 눈에 띄게
아프다. 사수 하나만 주던 시절에는 전 전략이 글자 그대로 같은 판을 돌려 튜토리얼이
아무 선택도 가르치지 않았는데, 정반대 축인 살수를 같이 주면서 첫 판단이 생겼다.

|---|---|---|---|
| 총통 몰빵 | 0% | 16.9 ± 0.4 | 0.0 |
| 포수 몰빵 | 5% | 19.1 ± 0.2 | 0.1 |
| 균형 (사수·총통·화차) | 100% | 20.0 ± 0.0 | 4.0 |
| 균형 + 거마작 | 100% | 20.0 ± 0.0 | 10.0 |
| 균형 + 기고 | 100% | 20.0 ± 0.0 | 18.0 |
| 균형 · 여덟 종 전부 | 100% | 20.0 ± 0.0 | 5.0 |
| 적응형 · 거마작 0기 | 65% | 19.6 ± 0.5 | 1.1 |
| 넓히기 우선 (건설 20기) | 100% | 20.0 ± 0.0 | 11.5 |
| 키우기 우선 (6기 만렙) | 0% | 19.0 ± 0.0 | 0.0 |

경로가 셋이라 **넓히기(20기)가 강한 것**도 설계대로다. 기고가 여기서 가장 크게 값을
한다(생명 4.0 → 18.0) — 기물이 많이 깔릴수록 곱셈이 커지기 때문이고, 기고를 S5
보상으로 둔 이유가 이것이다.

## 6. 거마작에 대한 별도 기록 — 「언제 짓는가」에 답을 붙인 과정

이번 판의 가장 큰 밸런스 변경이라 따로 남긴다.

**증상.** 6스테이지 체제로 넓힌 직후, 거마작을 지을수록 결과가 나빠졌다.
S3에서 `적응형 · 거마작` 0기 100% / 1기 65% / 2기 0% / 3기 0%로 **완벽하게 단조 감소**했다.
거마작을 처음 손에 쥐는 스테이지가 하필 거마작을 지으면 지는 스테이지였던 셈이다.

**틀린 진단 두 개.**
- *경제 문제인가?* `--income` 스윕으로 확인했다. ×1.45까지 올려도 0기(생명 15.0)가
  3기(6.8)를 계속 이겼고, ×1.3부터는 궁수대 몰빵이 92% 클리어해 "몰빵은 막힌다"는
  성질이 먼저 깨졌다. **경제는 원인이 아니다.**
- *배치 문제인가?* `pickSpot(preferEarly)`가 상위 40% 커버리지 안에서 가장 앞쪽 자리를
  고르는 것을 확인했다. 합리적인 규칙이라 여기도 아니다.

**진짜 원인.** 거마작에는 "언제 짓는가"의 답이 없었다. 보병에게도 기병에게도 똑같이
−55% 걸리는 균일 감속은, 딜이 0인 대가로는 어느 웨이브에서도 충분히 좋지 않았다.
AI가 거마작을 지으면 그냥 **화력 한 기를 버리는 것**이었다.

**고친 방식.** 감속을 기마에 몰아줬다. `TowerLevelDef.cavalrySlow`를 추가해
`enemy.def.flying`일 때만 `slowAmount + cavalrySlow`(상한 0.95)를 적용한다.

| 레벨 | 보병 감속 | 기마 감속 |
|---|---|---|
| 1 | −52% | **−78%** |
| 2 | −64% | **−90%** |
| 3 | −74% | **−95%** |

이건 튜닝이기 전에 **고증**이다. 거마작(拒馬柵)은 이름 그대로 *말을 막는* 물건 —
통나무에 창을 꽂아 기병의 돌격선을 끊는 장애물이지 보병용 방어물이 아니었다.
보병에게나 기병에게나 똑같이 듣던 이전 수치가 오히려 어색했다.

같은 논리로 시뮬레이터 AI의 판단 기준도 바꿨다. 전에는 `웨이브 ≥ 5`면 조건 없이 한 기를
지었는데, 이제 **다가오는 웨이브의 기마 HP 비중이 20%를 넘을 때만** 짓는다.

**결과.** S3의 단조 감소가 사라졌다.

| S3 전략 | 변경 전 | 변경 후 |
|---|---|---|
| 적응형 · 거마작 1기 | 65% | **95%** |
| 적응형 · 거마작 2기 | 0% | **100%** |
| 적응형 · 거마작 3기 | 0% | **100%** |
| 균형 · 옛 다섯 종만 | 0% | **90%** |
| 균형 · 일곱 종 전부 | 85% | **100%** |
| 키우기 우선 | 0% | **100%** |

**남은 것.** `균형 + 거마작`만 S3에서 0%로 남았다(5장 참고). 거마작을 더 많이 짓는 빌드가
100%인 이상 거마작의 문제가 아니라고 판단해 그대로 뒀다.

## 7. 살수와 기고를 넣으며 배운 것

### 살수 — 짧은 사거리는 데이터가 아니라 배치를 깨뜨린다

살수를 넣자마자 **방어가 전혀 없는 첫 판에서도 2웨이브에 죽었다.** 기물 셋을 짓고 아무것도
죽이지 못해 골드가 108G에서 멈춘 채였다. 수치를 의심했지만 원인은 시뮬레이터의 배치
알고리즘이었다 — 모든 자리를 **평균 사거리 3.2칸 하나로** 순위 매겨 돌려쓰고 있었고,
3.2칸 기준 1위 자리는 경로에서 떨어져 긴 구간을 얕게 덮는 곳이라 **1.9칸으로는 경로에
아예 닿지 않았다.**

사거리별로 순위를 다시 매기게 고치자 살수 몰빵이 첫 판을 100% 클리어했다(생명 16.1).
**새 기물의 수치를 의심하기 전에 그 기물이 측정 가능한 상태인지 먼저 봐야 한다**는
교훈으로 남긴다.

### 살수 — "다음 한 웨이브만 보는" AI가 만든 함정

적응형 AI에 "맨몸 물량이면 살수"라는 갈래를 느슨하게 넣었더니 **S2가 100% → 0%로
무너졌다.** 이 AI는 다가오는 한 웨이브만 보는데 **초반 웨이브는 어느 판이든 맨몸**이라,
3기를 깔아 놓고 뒤쪽 갑주 웨이브에서 통째로 놀린 것이다.

조건을 셋으로 조였다 — 기반이 이미 있고(5기 이상), 맨몸이고, 기병이 아닌 지상 물량일
때만, 최대 2기. S2가 100%로 돌아왔다. 백병이 갑주·산개 **둘 다**에 깎이는 유형이라
이 함정이 유독 깊었다.

### 기고 — 배치 규칙 자체가 다른 첫 기물

기고는 적을 겨누지 않으므로 커버리지 순위가 무의미하다. `pickCommandSpot`을 따로 두어
**이미 깔린 기물이 가장 많이 들어오는 자리**를 고르게 했고, 곱할 것이 하나도 없으면
아예 짓지 않는다. 그래서 `기고 몰빵` 대조군은 **기물을 0기 짓고 1웨이브에 진다** —
의도한 대로이고, "주변에 기물이 없으면 아무것도 안 한다"가 수치로 확인된 자리다.

값은 확실히 한다. `균형 + 기고`는 `균형 + 거마작`에 기고 하나를 더한 순환이라
둘의 차이가 곧 기고의 값이다 — **S6에서 85% → 95%**, S4에서는 남은 생명이 5.5 → 17.8로 오른다.

### 거마작 몰빵이 정묘호란을 30% 클리어하던 문제

딜이 0에 가까운 서포터가 판을 혼자 푸는 것은 조합 설계가 깨졌다는 뜻이다.
먼저 감속 상한을 0.95 → 0.85로 내려 봤는데 **30%가 그대로였고 조합 빌드만
90% → 45%로 떨어졌다** — 원인이 감속이 아니라는 뜻이다.

진짜 원인은 거마작 자신의 딜이었다. 광역 1.55칸에 초당 1.2발이면 14기를 깔았을 때
딸린 딜만으로 16웨이브를 버틴다. L3 딜을 8 → 5로 깎으니 몰빵이 W2에서 죽었고,
조합 빌드는 거의 영향을 받지 않았다(2기만 쓰므로). 상한은 0.95로 되돌렸다.

### 압박을 낮추면 오히려 조합이 약해진다

S6의 여러 빌드가 **정확히 W19에서** 막히기에 잡몹 수를 8% 줄여 봤다. 결과는 반대였다 —
`균형 + 거마작` 85% → 65%, `옛 일곱 종만` 70% → 25%. **적을 줄이면 현상금도 줄어**
기물을 덜 짓게 되기 때문이다. 압박을 되돌리고 웨이브 보상을 10% 올리자 제자리로 왔다.

이 프로젝트에서 같은 함정에 두 번 빠졌으므로 규칙으로 적어 둔다:
**후반 스테이지가 빡빡할 때 손대야 하는 것은 HP가 아니라 경제다.**

## 8. 세 번을 헛짚고 나서야 찾은 것 — 거마작은 자리가 틀렸다

이 프로젝트에서 가장 오래 끈 문제이고, 원인은 밸런스가 아니었다.

**증상은 판마다 모양을 바꿔 가며 계속 나왔다.**
- 6스테이지로 넓힌 직후 — S3에서 `적응형 · 거마작` 0기 100% / 1기 65% / 2기 0% / 3기 0%
- 기마 감속을 넣어 고친 뒤에도 — S6에서 1/2/3기가 전부 0%, 0기만 90%
- 세기를 깎자 — S5에서 **거마작이 들어간 빌드만 전부 0%**, 없는 빌드는 92~100%

**세 번 헛짚었다.**
1. *경제인가?* `--income` ×1.45까지 올려도 0기가 3기를 계속 이겼다. 아니었다.
2. *감속이 약한가?* 세기를 올렸다 내렸다 하며 상한을 0.65 / 0.80 / 0.95로 바꿔 봤지만
   어느 값에서도 "지을수록 진다"가 사라지지 않았다.
3. *지속이 짧은가?* 지속을 줄였다가 오히려 더 나빠졌다 — 이건 **이 문서 6장과 GDD에
   이미 적혀 있던 규칙을 스스로 어긴 것**이었다(감속은 타워를 지나간 뒤에도 남아야 한다).

**진짜 원인은 배치 규칙이었다.** 시뮬레이터가 거마작에만 「커버리지 상위 40% 중
가장 앞쪽」이라는 규칙을 따로 적용하고 있었다. "감속이 뒤쪽 기물 전부에 이득이 되니
앞에 두자"는 논리는 그럴듯했지만, **2갈래 맵에서 경로 앞쪽은 적도 덜 지나가고 기물도
없는 곳**이라 곱할 것이 없었다.

규칙 한 줄을 지우자:

| S5 정묘호란 | 앞쪽 우선 | 커버리지 1위 |
|---|---|---|
| 균형 + 거마작 | **0%** | **100%** (생명 15.4) |
| 적응형 · 거마작 2기 | **0%** | **100%** (생명 12.8) |

**그리고 이 발견이 지적을 뒤집었다.** 올바른 자리에서 다시 재니 거마작은 약한 게
아니라 **너무 강했다** — 병자호란을 생명 20/20 무손실로 클리어했다. 여러 판에 걸쳐
"약해서 안 쓰인다"고 재고 있던 수치가 전부 잘못된 자리에서 나온 것이었고, 그래서
계속 강화하는 방향으로 손대고 있었다. 제대로 측정한 뒤에야 감속을 −74% → −28%
(기마 −95% → −46%)로 깎아 지금의 모양(도움은 되지만 결정적이지는 않은)에 도달했다.

**남기는 교훈**: 어떤 기물이 계속 이상한 값을 내면 **수치를 만지기 전에 그 기물이
제대로 측정되고 있는지 먼저 봐야 한다.** 사거리 1.9의 살수도 같은 함정이었다(7장).
두 번 다 원인은 `sim/coverage.ts`였지 `data/towers.ts`가 아니었다.

## 9. 겹치는 기물은 지운다 — 불랑기포 제거

"기물끼리 특색이 겹쳐서 뭘 골라야 유리한지 감이 안 온다"는 지적을 받고, 감으로
답하는 대신 **골드당 유효 DPS를 여덟 개 적 원형에 대해 계산**했다(만렙 총투자 기준,
광역은 뭉친 적 보정 포함).

| 기물 | 투자 | 졸병 | 갑병 | 별동대 | 간자 | 철기 | 경기병 | 충차 | 보스 |
|---|---|---|---|---|---|---|---|---|---|
| 총통 | 395 | **249.9** | **249.9** | **87.5** | **50.0** | **249.9** | **199.9** | **174.9** | **137.4** |
| 불랑기 | 530 | 231.6 | 231.6 | 81.1 | 46.3 | 231.6 | 185.3 | 162.1 | 127.4 |

**여덟 칸 전부에서 총통보다 낮은데 135G 더 비쌌다.** 광역이라는 이점을 계산에 넣고도
그랬다 — 총통의 한 방(94)이 불랑기(44)의 두 배가 넘어서, 뭉친 적 보정으로도 뒤집히지
않았다. 완전한 하위호환이라 없앴다.

같은 계산이 **포수의 정체성도 거짓말**이라고 알려 줬다. "갑주에 강한 관통"이라던
기물이 갑주 18짜리 철기 상대로 **사수 66.1 vs 포수 64.2**로 지고 있었다. 둘 다 관통이라
축이 통째로 겹쳐 있었던 것이다. 한 발의 무게를 올려 갈랐다 — 지금은 맨몸에서 사수가
두 배 넘게 낫고(264.5 vs 107), 갑주 18부터 포수가 앞선다(66.1 vs 68.5), 갑주 22에서는
2.7배 앞선다.

여기서도 한 번 넘어졌다. 한 발을 62까지 올렸더니 **포수 몰빵이 병자호란을 100%
(생명 15.6) 클리어했다** — 관통이라 산개 80%를 통째로 무시하는데 사거리 4.7이 거의
모든 구간을 덮은 탓이다. 데미지가 아니라 **사거리**를 4.3으로 깎아 잡았다(5%로 복귀).
이 게임에서 커버리지가 DPS보다 강하다는 것이 세 번째로 확인된 자리다.

## 10. 너프도 지나칠 수 있다 — 거마작을 기마 축으로만 되돌린 과정

8장에서 배치를 고치고 나니 거마작이 사기라는 것이 드러나 깎았는데, **그 너프가
반대쪽으로 지나쳤다.** 증상은 해금 규칙이 깨진 것으로 나타났다 — 거마작은 삼포왜란의
클리어 보상인데, 정작 처음 쓰는 니탕개의 난에서 **넣은 쪽이 더 나빴다**(45% → 32%).
"새로 열린 기물은 다음 스테이지에서 곧바로 쓰인다"가 이 프로젝트의 해금 규칙이다.

되돌리는 방향이 하나가 아니라서 세 축을 따로 쟀다. 각 60판, `균형(3종)` 대비
`균형 + 거마작`의 차이다.

| 무엇을 올렸나 | S3 | S4 생명 | S5 | S6 생명 |
|---|---|---|---|---|
| (그대로) 보병 18~28% · 기마 28~46% | **−13%** | +7.0 | 85% | 7.0 |
| 보병·기마 함께 | −12% | +7.5 | 97% | 8.0 |
| 지속만 (4~5.6 → 5.2~7.2초) | **−22%** | +7.6 | 95% | 7.0 |
| **기마만** (28~46% → 38~62%) | **±0%** | +7.0 | **100%** | **10.0** |

**세기를 더 올리면 절벽이 있다.** 보병·기마를 함께 조금만 더 올리면 S6 생명이
8.0에서 **18.0으로 튄다**(만점 20.0). 최종 스테이지가 통째로 시시해지는 지점이고,
애초에 "사기"라는 지적을 받은 상태가 그것이다. 그 절벽 아래에서 값을 하는 축이
기마였다.

**지속은 이 문제의 지렛대가 아니었다.** 6장에서 "지속이 세기보다 중요하다"고 적어
뒀지만, 그건 지속이 **너무 짧을 때** 곱셈이 성립하지 않는다는 뜻이지 늘릴수록
좋다는 뜻이 아니었다. 4~5.6초는 이미 충분했고, 더 늘리자 S3가 −22%로 오히려
나빠졌다. 규칙에는 유효 범위가 있다.

**보병 감속은 손대지 않았다.** 거마작(拒馬柵)은 이름 그대로 말을 막는 물건이라
기마 축만 올리는 것이 고증에도 맞고, 화차가 기마를 조준하지 못하는 것과 짝을 이뤄
"기마 웨이브에는 거마작"이라는 판단을 더 선명하게 만든다. 축을 하나만 움직였더니
정체성이 흐려지는 대신 오히려 또렷해졌다.

**남은 것.** S3의 +35%(20판)와 ±0%(60판)는 판수에 따라 흔들린다. 부호가
음수에서 벗어난 것은 두 판수에서 모두 확인했지만, 이 스테이지는 임계값 근처라
절대값으로 읽으면 안 된다.

## 11. 열린 질문

- **`적응형 · 거마작 0기`가 1위이던 문제는 8장에서 해소됐다.** 지금은 S5 50% vs 2기 80%,
  S6 65% vs 2기 100%로 뒤집혀 있다 — 원인이 배치였다는 증거이기도 하다.
- **별파진이 정말 필요한가?** 최종 스테이지도 중독 없이 100% 클리어된다.
  **해금 보상 중 필수성이 검증되지 않은 유일한 기물**로 남아 있다 — 9장의 계산에서도
  모든 적에게 101.4로 완전히 평평해서, 특정 적을 겨냥한다는 느낌이 약하다.
- **살수의 자리가 판마다 극단적으로 갈린다.** S5에서는 값을 하지만(생명 1.4 → 8.6)
  S6에서는 같은 순환에 넣으면 100% → 0%다. 갑주 18·산개 80%가 기본인 판에서 백병이
  둘 다에 깎이는 것은 설계대로지만, **"맨몸 물량"이라는 자리가 후반에 사라진다**는 뜻이라
  잡몹 구성으로 그 자리를 남겨 줄지 검토가 필요하다.
- **7장의 「아홉 종 전부」 결과**는 기물을 더 늘리는 데 대한 제동이다. 14기 예산에
  아홉 종은 이미 얇다.
- **화차의 기마 페널티**는 여전히 미검증. 화차 몰빵이 기마 등장 전에 화력 부족으로 죽는다.
- **S1이 사실상 무손실**이다. 튜토리얼로는 맞지만 한 번도 새지 않으면 생명 시스템 자체를
  배우지 못한다. 마지막 웨이브만 살짝 아프게 할지 검토.
- **타겟팅 우선순위** 축 미검증.
- **「키우기」 빌드**는 S5 0% / S6 0%로 후반에 무너진다. 경로가 길고 갈라질수록
  커버리지가 레벨보다 중요하다 — 이건 버그가 아니라 성립한 성질로 읽는다.
