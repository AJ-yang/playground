# 게임 설계 문서 (GDD) — 조선 방어전

> 경로형 타워디펜스. 이 문서는 "왜 이렇게 만들었는가"를 남기는 곳이고,
> 실제 수치는 `src/data/` 아래 파일이 단일 진실 공급원(single source of truth)이다.
> 수치를 바꿀 때는 데이터 파일을 고치고, 의도가 바뀌면 이 문서를 고친다.

---

## 1. 한 줄 요약

정해진 경로를 따라 밀려오는 20개 웨이브의 적을, 길 옆 빈 땅에 타워를 지어 막는다.
**"어떤 타워를 짓느냐"가 아니라 "어떤 조합을 어디에 짓느냐"** 가 승패를 가른다.

## 2. 참고한 게임과 각각에서 가져온 것

| 게임 | 가져온 설계 | 이 프로젝트에서의 구현 |
|---|---|---|
| **Kingdom Rush** | 소수의 타워 아키타입 + 명확한 상성. 타워 4종만으로 깊이를 만든다 | 기물 9종. 각자 "절대 못 하는 것"을 하나씩 부여 |
| **Kingdom Rush** | 웨이브 사이 준비 시간 + 조기 소환 보너스 | `prepTime` 카운트다운, 남은 시간 × 2G 보너스 |
| **Bloons TD 6** | 타겟팅 우선순위(First/Last/Strong/Close)를 플레이어가 지정 | 타워별 `targetPriority`, 패널에서 순환 전환 |
| **Bloons TD 6** | 적의 "속성"(납·위장 등)이 특정 타워를 무력화 | 갑주 / 산개 / 기마 3축 방어 스탯 |
| **Plants vs. Zombies** | 새 위협을 한 번에 하나씩, 경고와 함께 도입 | 웨이브 `warning` 필드, 4·6·7·10·12·14웨이브에서 신규 위협 |
| **Dungeon Defenders** | 판매 환급으로 빌드 교체를 허용 (실수 회복 가능) | 투자 골드의 70% 환급 |
| **Defense Grid** | 유출(leak) 시 즉사가 아니라 생명 차감 → 실패해도 계속 플레이 | 생명 20, 적 종류별 `leak` 값 (보스는 10) |

**의도적으로 빼기로 한 것**

- **미로 짓기(BTD/Desktop TD식 경로 변경)** — 경로가 고정이라 A* 재계산·경로 봉쇄 검증이 필요 없다.
  최적해가 "미로 최대화" 하나로 수렴해 타워 조합의 의미가 줄어드는 문제도 피한다.
- **영웅 유닛 / 병영 유닛** — 이동·교전 AI가 필요해 코어 규모를 크게 키운다. 로드맵 2단계로 미룸.
- **특수기(운석·증원 등 쿨다운 액티브)** — 코어 검증 뒤 추가. 로드맵 1단계.

## 3. 핵심 루프

```
준비 (prepTime 초)
  ├─ 다음 웨이브 구성을 패널에서 확인
  ├─ 골드로 타워 건설 / 업그레이드 / 판매
  └─ [다음 웨이브] 조기 소환 → 남은 초 × 2G 보너스
        ↓
교전
  ├─ 적이 경로를 따라 진행, 타워가 자동 사격
  ├─ 처치 → 즉시 현상금 골드
  └─ 완주 → 생명 차감
        ↓
클리어 보상 골드 → 다시 준비
        ↓
20웨이브 클리어 = 승리 / 생명 0 = 패배
```

**플레이어가 매 웨이브 내리는 결정 3가지**

1. **넓히기 vs 키우기** — 새 타워를 지을까, 기존 타워를 업그레이드할까
   (업그레이드는 골드 대비 DPS가 좋고, 신규 건설은 커버리지가 넓어진다)
2. **조합 맞추기** — 다음 웨이브의 방어 속성에 맞는 타워가 사거리 안에 있는가
3. **지금 부를까** — 조기 소환 보너스를 먹을 만큼 방어선이 준비됐는가

## 4. 밸런스의 축

### 4.1 데미지 타입 × 방어 스탯

이 게임의 모든 상성은 아래 두 줄에서 나온다 (`src/game/Enemy.ts`의 `takeDamage`).

```
관통 데미지 = max(1, 공격력 − 갑주)                 ← 고정 감소. 저데미지·고연사 기물이 크게 손해
화약 데미지 = max(1, 공격력 × (1 − 산개))           ← 비율 감소. 고데미지 기물도 똑같이 손해
순수 데미지 = 공격력                                 ← 아무것도 막지 못한다 (별파진의 쇳조각)
백병 데미지 = max(1, 공격력 × (1 − 산개) − 갑주)     ← 둘 다 걸린다 (살수의 칼)
```

**고정 감소 vs 비율 감소를 일부러 다르게 잡은 이유:**
갑주는 "한 방이 약한 타워"를 죽인다 (사수 L3 24딜 vs 철기 갑주 18 → 6딜, **−75%**).
산개는 "한 방이 센 타워"도 똑같이 죽인다 (총통 L3 94딜 vs 간자 산개 80% → 18.8딜, **−80%**).
두 방어가 서로 다른 방식으로 아프기 때문에, 한쪽 타워만 도배하면 반드시 벽에 부딪힌다.

이 전제는 **사수가 실제로 저데미지일 때만** 성립한다. 초기 수치에서는 사수 L3 데미지가
36으로 총통 L1(32)보다 높아 전제 자체가 깨져 있었고, 시뮬레이션에서 사수 몰빵이 무손실
클리어했다. 자세한 경위는 [`BALANCE.md`](BALANCE.md) 3장.

### 4.2 일곱 기물의 역할

| 타워 | 타입 | 기마 | 특징 | 카운터당하는 적 |
|---|---|---|---|---|
| 사수 70G | 관통 | ○ | 골드 대비 DPS 1위, 저데미지 고연사 (L3 24×2.7) | 갑병(갑주 12), 철기(갑주 18) |
| **살수 80G** | **백병** | ○ | 값싼 근접 광역, 사거리 최단 (L3 56×0.85, 반경 1.2) | 갑주·산개 **양쪽 모두** |
| **기고 90G** | — | — | **딜 0.** 반경 안 아군 공격속도 +18~35% | (주변에 기물이 없으면 무용) |
| 총통 110G | 화약 | ○ | 갑주 완전 무시, 느리고 비쌈 (L3 94×1.05) | 별동대(65%), 간자(80%) |
| 화차 130G | 관통·광역 | **✕** | 지상 물량 정리 최강, 발사 매우 느림 | 모든 기마 유닛 |
| 거마작 75G | 화약·광역 | ○ | 딜 거의 없음(L3 8), 감속 −74% / 7초 · **기마에는 −95%** | (직접 카운터 없음 — 대기병 서포터) |
| 별파진 100G | **순수** | ○ | 직접 딜 거의 없음, 중독 28/s × 4초. 갑주도 산개도 통과 | (직접 카운터 없음 — 탱커 해답) |
| 포수 125G | 관통 | ○ | **사거리 최장**(L3 4.7), 고데미지 저연사 (L3 48×0.92) | 간자(80%), 궁기병(55%) |
| 불랑기 155G | 화약·광역 | ○ | 기병에도 닿는 좁은 광역 (L3 44, 반경 1.05) | 철기 무리 |

**거마작을 넣은 이유**: 나머지가 전부 "직접 딜"이라 선택이 단순한 상성 퀴즈가 된다.
거마작은 자기 DPS가 아니라 *다른 타워의 유효 사격 시간*을 늘리는 곱셈 축이라,
"어디에 놓을 것인가"라는 위치 판단 문제를 게임에 추가한다. 코너 안쪽에 놓으면
적이 감속된 채로 여러 타워의 사거리를 통과하게 만들 수 있다.

**감속은 기마에 몰아줬다** (`TowerLevelDef.cavalrySlow`). 보병 −52~74%, 기마 −78~95%.
곱셈 축은 "언제 짓는가"에 답이 없으면 그냥 화력 한 기를 버리는 것이 되는데, 균일 감속일
때 실제로 그랬다 — 시뮬레이션에서 거마작을 지을수록 클리어율이 단조 감소했다.
기마에 몰아주자 그 단조 감소가 사라졌다 ([`BALANCE.md`](BALANCE.md) 6장).

이건 튜닝이기 전에 **고증**이다. 거마작(拒馬柵)은 이름 그대로 *말을 막는* 물건이다 —
통나무에 창을 꽂아 기병의 돌격선을 끊는 장애물이지 보병용 방어물이 아니었다.
보병에게나 기병에게나 똑같이 듣던 이전 수치가 오히려 어색했다. **화차가 기마를 조준하지
못하는 것과 짝을 이뤄**, 기마 웨이브는 "화차를 빼고 거마작을 넣는" 판단을 강제한다.

**상태 이상은 중첩되지 않는다** — 감속도 중독도 가장 강한 것 하나만 적용하고 지속시간만
갱신한다 (`Enemy.applySlow` / `applyPoison`). 서포터 타워를 도배해 적을 정지시키거나
녹여버리는 퇴화 전략을 막기 위함이며, 그래서 두 타워 모두 1~2기가 최적이고 과투자는 손해다.

**감속 지속시간이 사거리보다 중요하다.** 지속이 짧으면 적이 거마작 사거리를 벗어나는 순간
감속이 풀려 뒤쪽 타워가 아무 이득을 못 본다. 서포터가 성립하려면 감속이 **타워를 지나간 뒤에도
남아야** 한다 — 검증 과정에서 지속을 2.2초 → 7초로 늘리고 나서야 거마작이 값을 하기 시작했다
([`BALANCE.md`](BALANCE.md) 4장).

### 4.3.1 보스

**스테이지 중간과 끝에 보스를 둔다.** 웨이브 하나를 "물량"이 아니라 "한 덩어리"로
바꿔 리듬을 끊는 장치다. 물량 웨이브는 커버리지로 풀지만 보스는 **집중 화력과 상성**으로
풀어야 해서, 같은 스테이지 안에서 서로 다른 질문을 던진다.

| 보스 | HP | 갑주 | 산개 | 정체성 | 등장 |
|---|---|---|---|---|---|
| 왜구 두목 | 1250 | 0 | 0 | 방어 없는 덩치 — 순수 화력 시험 | S1 W8 |
| 철갑 장수 | 2300 | **22** | 0 | 관통 완전 무력화 → 총통 강제 | S2 W10, S5 W8, S6 |
| 선봉 기병 | 1900 | 5 | 25% | **기마** — 화차 조준 불가 + 빠름 | S3 W7, S5 W14, S6 |
| 날랜 왜장 | 2100 | 0 | **78%** | 총통 몰빵 응징 → 활·조총 강제 | S4 W8 |
| 여진 대추장 | 2050 | 4 | **62%** | **기마 + 산개** — 활·조총 강제 | S3 W12 |
| 누차 | 3600 | 10 | 15% | 공성 망루 — 상성이 아니라 화력 총량 | S4 W14 |
| 팔기 중군 | 4400 | **18** | **52%** | 양면 저항 — 한쪽 화력으로는 못 녹인다 | S5 W16 |
| 팔기 대장 | 5200 | 14 | 45% | 최종 보스 | S6 W20 |

**보스도 실루엣 규칙을 따른다.** 전부 `boss`(가시 다각)를 쓰되 방어 표식이 스탯에서
파생되므로 갑주 보스에는 흰 테두리가, 산개 보스에는 보라 오라가 자동으로 뜬다.
형태만 보고 "무엇으로 때려야 하는가"가 여전히 읽힌다.

**중간 보스와 최종 보스의 leak을 다르게 잡았다.** 중간 보스는 2~4, 최종 보스는 10.
검증 과정에서 중간 보스 leak을 4~6으로 두자 S5가 **모든 전략 0%** 가 됐다 — 중간에
두 번 뚫리는 것만으로 생명 풀이 바닥나 최종 웨이브를 볼 수 없었다. 중간 보스는
"뚫리면 아프지만 판은 이어지는" 체크포인트여야 한다.

**보스를 넣을 때는 그 웨이브의 잡몹을 줄인다.** 처음에는 35~40%를 덜어냈는데,
S4에서 고속 물량이 사라지자 **총통 몰빵이 100% 클리어**해 버렸다 (거마작 해금의
필요성을 증명하던 지점이 무너졌다). 잡몹은 5~10%만 덜고 보스를 얹는 쪽이 옳다.

### 4.4 난이도 곡선 (20 웨이브)

| 구간 | 주제 | 플레이어가 배워야 하는 것 |
|---|---|---|
| 1–5 | 기본기 | 경로 커버리지, 골드 운용. 사수·살수만으로 넘어간다 |
| 6–10 | 방어 도입 | 갑주↔마법 / 산개↔물리 / 기마↔화차 상성 |
| 11–15 | 복합 | 상성이 반대인 적을 같은 웨이브에 섞음. 단일 빌드가 여기서 무너진다 |
| 16–20 | 총력전 | 물량+저항+기마 동시 압박, 마지막에 보스 |

**경제 튜닝** — 스테이지마다 골드가 0부터 다시 시작한다. 시작 골드는 270~520G,
수입은 처치 현상금 + 웨이브 클리어 보상 + 조기 소환 보너스로 들어온다.

경제는 이 게임에서 가장 민감한 축이다. 단일 20웨이브 시절에는 총 수입이 필요액의 2.5배여서
모든 몰빵 빌드가 무손실 클리어했고, 스테이지로 나눈 뒤에는 반대로 초반 골드가 말라
S2~S5가 전멸했다. 수치를 고칠 때는 `npm run sim -- --audit`으로 스테이지별 수입 곡선을
먼저 확인하고, `--income` / `--hp` 배율로 스윕한 뒤 확정값만 데이터에 반영할 것.

### 4.5 스테이지와 해금

게임은 스테이지 6개로 나뉜다. 선형 해금이라 앞 스테이지를 깨야 다음이 열린다.

**스테이지당 하나로 고정하지 않는다.** 처음에는 그렇게 잡았는데, 기물이 일곱으로
늘면서 그 규칙이 **스테이지 수를 정하는 쪽**이 돼 버렸다. 배우는 순서가 판의 개수를
강제하는 것은 앞뒤가 뒤바뀐 것이라 풀었다 — S1은 둘(총통·화차)을 연다. 다음 판이
갑주와 물량을 동시에 던지기 때문이다. 지켜야 하는 것은 개수가 아니라
**"열린 것은 다음 판에서 곧바로 쓰인다"** 는 규칙이다.

| 스테이지 | 맵 | 경로 | 웨이브 | 시작 시 보유 | 클리어 보상 |
|---|---|---|---|---|---|
| S1 왜구의 노략 | 완만한 S자 | 1 | 8 | 사수·살수 | **총통 · 화차** |
| S2 삼포왜란 1510 | 촘촘한 지그재그 | 1 | 10 | +화차 | **거마작** |
| S3 니탕개의 난 1583 | 두 출발점이 합류 | **2** | 12 | +거마작 | **포수** |
| S4 임진왜란 1592 | 길게 되접히는 나선 | 1 | 14 | +포수 | **별파진 · 기고** |
| S5 정묘호란 1627 | 두 갈래가 합류 | **2** | 16 | +별파진·기고 | **불랑기** |
| S6 병자호란 1636 | 세 방향 동시 압박 | **3** | 20 | 전부 | — (최종) |

**설계 규칙: 새로 열린 기물은 다음 스테이지에서 곧바로 필요해야 한다.** 그러지 않으면
해금은 그냥 숫자가 늘어나는 일이 되고 배우는 게 없다. 그래서 각 스테이지의 신규 위협은
직전 보상이 답이 되도록 배치했다 — S2의 갑병·방패병에는 총통, S3의 기병에는 화차가
아닌 것, S4의 간자(산개 80%)에는 조총, S5의 양면 저항에는 별파진, S6의 갑주 두른
기병 무리에는 불랑기.

이 규칙이 실제로 성립하는지가 밸런스 검증의 핵심 질문이다. S1의 총통은 명확히 확인됐고
(S2에서 사수 몰빵 0% vs 총통 몰빵 100%), S2의 거마작도 S5에서 같은 고정 순환 빌드의
클리어율을 10% → 50%로 가른다. 반면 **별파진와 불랑기는 아직 필수성이 검증되지
않았다** — [`BALANCE.md`](BALANCE.md) 8장 참고.

**진행도는 localStorage에 저장된다** (`game/Progress.ts`). 저장소를 주입받는 구조라
헤드리스 시뮬레이터와 테스트는 메모리 저장소를 쓴다.

### 4.6 난이도 — 바뀌는 축은 하나뿐

| 난이도 | 적 체력 | 검증 |
|---|---|---|
| 쉬움 | 70% | 조합 빌드 전 스테이지 100% (S5 생명 5.0) |
| 보통 | 100% | 기준. 아래 9장의 표가 전부 이 값 |
| 어려움 | 125% | **조기 소환으로 경제를 굴리는 빌드만** 전 스테이지 클리어 (S5 60%) |

**웨이브 구성·적 종류·타워 수치는 난이도와 무관하게 동일하다.** 이유가 둘이다.

1. 이 게임의 설계는 "어떤 조합으로 어떤 상성을 푸는가"에 있다. 난이도가 적 종류나
   방어 스탯을 바꾸면 **풀이 자체가 달라져** 쉬움에서 배운 것이 어려움에서 통하지 않는다.
2. 검증 비용. 축이 하나(체력 배율)뿐이면 다른 난이도를 배율 스윕으로 읽어낼 수 있다.
   난이도마다 웨이브가 다르면 1,300판 검증을 난이도 수만큼 다시 해야 한다.

**어려움 배율은 스윕으로 정했다.** 처음 잡은 145%는 시뮬레이터 AI 기준 S2부터 전멸했다 —
적을 못 잡으면 현상금이 안 들어오고, 그러면 타워를 못 짓고, 다시 더 못 잡는 **경제
죽음의 나선**이다. 1.10 / 1.15 / 1.20 / 1.25를 스윕해 보니 일반 빌드는 1.15부터
무너지지만 조기 소환 보너스를 챙기는 빌드는 1.25까지 전 스테이지를 클리어했다.
그래서 어려움은 "화력이 아니라 **경제 운용**을 요구하는 난이도"로 정의된다.

**해금은 난이도와 무관하게 공유한다.** 쉬움으로 깬 사람도 다음 스테이지와 기물이
열린다 — 난이도는 진입 장벽이지 콘텐츠 잠금이 아니다. 다만 최고 기록은
`스테이지ID@난이도ID`로 따로 남긴다. 쉬움의 20과 어려움의 3을 같은 칸에 적으면
기록이 아무 의미가 없어진다.

**경로 수가 난이도를 크게 좌우한다.** 경로가 갈라지면 타워 커버리지가 그만큼 나뉘어,
같은 압박 수치라도 2갈래 맵은 1갈래보다 훨씬 어렵다. 맵을 추가할 때는 경로 수에 맞춰
압박을 다시 잡아야 한다.

## 5. 시각 언어 (아트 디렉션)

### 5.1 세계관: 조선의 전쟁 — 왜 이걸 골랐나

세계관을 두 번 갈아엎었다. 처음은 **중세 판타지**, 다음은 **한국 민속(달밤의
귀신 행렬)**, 지금이 **조선의 전쟁**이다. 두 번 다 아트만 바뀌고 밸런스는 한 줄도
안 바뀌었다 — 매번 1,300판 시뮬레이션 결과가 교체 전과 **완전히 동일**했다.
이게 가능한 이유는 그림이 `render/art.ts` 한 파일에, 수치가 `data/`에 따로
있기 때문이다.

**바꾼 이유는 진부함이 아니라 구조였다.** 앞의 두 세계관은 「밀려오는 것들을
막는다」는 상황만 있고 **왜 점점 세지는가**에 대한 답이 없었다. 귀신이 왜
스테이지마다 강해지는지, 내 기물이 왜 다섯 개뿐인지는 그냥 게임의 규칙이었다.

조선의 전쟁은 그 두 가지를 **역사가 대신 설명해 준다.**

| 스테이지 | 사건 | 적이 세지는 이유 | 새로 열리는 기물 | 그 기물이 실제로 생긴 때 |
|---|---|---|---|---|
| S1 | 왜구의 노략 | 갑옷 없는 잡졸 | 사수·살수 → **총통·화차** | 승자총통 1575 · 문종 화차 1451 |
| S2 | 삼포왜란 (1510) | 갑주를 두르고 왔다 | **거마작** | 대기병 방책 |
| S3 | 니탕개의 난 (1583) | 여진 기병이 두 길로 | **포수** | 조총, 1592년 이후 주력 |
| S4 | 임진왜란 (1592) | 대군이 북상, 성벽에 사다리 | **별파진 · 기고** | 이장손 1592 · 형명 체계 |
| S5 | 정묘호란 (1627) | 기병이 벌판을 덮는다 | **불랑기** | 명 경유 도입, 16세기 |
| S6 | 병자호란 (1636) | 팔기군 총력 | — (최종) | — |

**해금 순서가 곧 기술사(技術史)다.** 활 → 총통·다연장 로켓 → 대기병 방책 →
개인 화기 → 시한 작렬탄 → 후장식 화포. 그리고 게임의 설계 규칙("새로 열린 기물은
다음 스테이지에서 곧바로 쓰인다")이 역사와 같은 방향을 가리킨다 — 왜구를 겪고 얻은
총통이 삼포왜란의 갑주를 뚫고, 거기서 얻은 거마작이 니탕개의 여진 기병을 묶고,
임진왜란에서 노획해 배운 조총이 그다음 전쟁의 산개를 뚫는다.

**한 판에 한 종씩이라는 규칙은 두지 않았다.** S1은 두 종을 한꺼번에 주고 S6는 아무것도
주지 않는다. 기준은 개수가 아니라 *열린 것이 다음 판에서 곧바로 쓰이는가*이며, 첫 판을
사수 하나로 끝내야 "경로를 덮는다"는 기본기만 가르치는 튜토리얼이 성립한다.
**설계상의 필요와 역사적 순서가 같은 방향을 가리키는 것**이 이 세계관을 고른
가장 큰 이유다.

밸런스 축의 대응도 앞의 두 세계관보다 낫다.

| 밸런스 축 | 중세 판타지 | 조선의 전쟁 |
|---|---|---|
| 물리 (고정 감소) | 화살 | **관통** — 화살과 탄환. 갑주가 두께로 막는다 |
| 마법 (비율 감소) | 마법 투사체 | **화약** — 폭발. 두께로는 안 막히지만 흩어지면 덜 맞는다 |
| 장갑 | 판금 갑옷 | **갑주** — 찰갑·두정갑 |
| 마법저항 | 저항 로브 | **산개** — 대열을 풀고 흩어져 달리는 것 |
| 방어 무시 | 독 | **쇳조각** — 별파진의 파편. 갑주도 산개도 상관없다 |

"흩어져 달리면 폭발이 덜 맞는다"는 마법저항보다 설명이 필요 없고, 실제로
병자호란에서 청 기병의 기동이 조선의 화포를 무력화한 것도 같은 이유다.

**「공중」을 「기마」로 바꿨다.** 조선의 전장에 나는 것은 없다. `flying` 플래그는
그대로 두고 의미만 갈았다 — 화차는 고정 거치식이라 방향을 바꾸려면 수레째
돌려야 하고, 그래서 달리는 기병을 조준하지 못한다. 이것도 실제 한계였다.
렌더러에서는 날개를 **흙먼지**로, 13px의 부양을 4px로 바꿨다(그대로 두면 말이
공중에 뜬다).

### 5.1.1 고증 방침

기준은 **"고증이 가독성을 해치지 않는 한 고증을 따른다"** 이고, 확인한 것과
추정한 것을 `render/art.ts` 머리말에 나눠 적었다.

- **자료로 확인** — 각궁의 이중 곡선 / 통아에 넣어 쏘는 편전 / 전립의 상모와 술 /
  승자총통의 놋쇠 테와 나무 자루 / 문종 화차의 구멍 100개 / 통나무를 X자로 엮은
  거마작 / 어떻게 던져도 가시 하나가 위를 향하는 마름쇠 / 죽통 심지로 시간을
  맞추는 별파진 / 미늘을 가죽끈으로 이은 찰갑 / 누런 바탕에 「帥」 한 글자를 쓴
  수자기 / 왜군 당세구족의 초승달 앞장식
- **추정** — 적 병졸의 세부는 특정 부대의 재현이 아니라 **역할의 기호**다.
  졸병·척후·갑병·별동대는 왜구·왜군·후금·청에 모두 있던 병종이라 어느 한쪽의
  복식으로 그리지 않았다. 나라가 드러나야 하는 것은 스테이지 이름과 보스이지
  잡졸이 아니다.

**일부러 하지 않은 것 — 실존 인물을 보스로 만들지 않았다.** 병자호란의 총사령은
청 태종이지만 최종 보스는 「팔기 대장」이라는 **직책**으로만 둔다. 400년 전
사람이라 해도 실명을 붙여 때려잡는 표적으로 삼는 것은 이 게임이 할 일이 아니다.
전쟁을 다루면서 특정 민족을 괴물로 그리지 않으려는 이유도 같다 — 적은 사람이고,
그래서 전부 사람의 형태로 그렸다.

### 5.2 원칙: 시각 속성은 테마가 아니라 규칙을 나른다

화면의 모든 형태·표식은 **게임 규칙 하나씩에 대응한다.** 멋있어 보이려고 넣은
요소는 없다. 3배속에서 40마리가 몰려올 때 "저건 화차가 못 때리는 놈"이
즉시 읽히지 않으면 상성 설계 전체가 무의미해지기 때문이다.

| 화면에 보이는 것 | 나르는 규칙 |
|---|---|
| **실루엣** (아래 5.3) | 적의 방어 유형 → 어떤 타워가 필요한가 |
| **날개 + 부양 + 작고 진한 그림자** | 기마 유닛 → 화차 조준 불가 |
| 본체를 감싼 같은 실루엣의 밝은 테두리 | 갑주 있음 |
| 보라 점선 오라 | 산개 있음 |
| 하늘색 링 | 지금 감속 걸림 |
| 연두 점선 링 | 지금 중독 — 방어 무시 피해 진행 중 |
| 기물 7종의 무기 (편전·탄환·신기전·마름쇠·진천뢰) | 기물 종류 |
| 타워 받침 옆 점 개수 + 건물 크기 | 타워 레벨 |
| 무기 회전 + 발사 반동 + 머즐 플래시 | 지금 누구를 겨누고 쐈는가 |
| 화면 가장자리 붉은 비네트 · 테두리 | 생명이 얼마나 위험한가 |

**위험 표시는 한 겹으로만 그린다.** 위험도 비네트와 유출 플래시가 각각 보드를
덮던 시절에는, 생명이 3일 때 보스가 유출되면 두 겹이 더해져 판이 통째로 불투명한
빨간색이 됐다 — 티는 확실히 났지만 그 0.6초 동안 플레이가 불가능했다. 지금은 두
효과의 **세기만 합치고 그림은 한 번**, 그것도 가장자리 가중으로 그린다.
판 가운데는 어떤 상황에서도 보여야 한다.

### 5.3 실루엣 = 방어 유형

**색이 아니라 형태에 정보를 싣는다.** 이유가 두 가지다.

1. 색각 이상 사용자도 "어떤 타워로 잡아야 하는가"를 판단할 수 있어야 한다.
2. 고배속에서 사람 눈은 색보다 실루엣을 먼저 읽는다.

| 실루엣 | 형태 | 의미 | 해당 적 |
|---|---|---|---|
| `basic` | 원 | 방어 없음 — 아무 타워나 통함 | 졸병 |
| `swift` | 진행 방향 쐐기 | 고속 — 감속 없으면 체류가 짧다 | 척후, 경기병 |
| `armored` | 육각 | 갑주 — 물리가 깎이니 **총통** | 갑병, 철기 |
| `warded` | 세로 마름모 | 산개 — 화약이 깎이니 **활·화차** | 별동대, 간자 |
| `bulwark` | 방패 오각 | 양면 저항 탱커 | 충차 |
| `boss` | 가시 다각 | 보스 | 팔기 대장 |

**기마 여부는 실루엣이 아니라 날개로 표현한다.** 방어 유형과 직교하는 축이기
때문이다 — 경기병(고속·기마)과 철기(갑주·기마)는 실루엣이 다르고
날개를 공유한다. 날개는 본체보다 넓게 펴고 밝은 테두리로 값을 분리했다.
같은 색·같은 명도로 그렸더니 실루엣이 하나로 뭉쳐 "날고 있다"가 읽히지 않았고,
척후(지상 쐐기)과 경기병(기마 쐐기)이 색으로만 구분되는 상태가 됐다.

### 5.4 지켜야 하는 규칙

- **`EnemyDef.silhouette`은 실제 스탯과 반드시 일치시킨다.** 형태가 정보를 나르는
  구조라, 여기가 어긋나면 플레이어가 화면을 보고 잘못된 타워를 짓는다.
  갑주 지배적 → `armored`, 산개 지배적 → `warded`, 둘 다 → `bulwark`.
- **방어 표식은 실루엣에서 파생시킨다.** 별도 임계값을 두면 실루엣과 어긋난다.
  실제로 예전에는 `magicResist >= 0.5` 하드코딩 때문에 **산개 45%인 보스에
  마법 표식이 안 떴다** — 설명문에는 "모든 방어를 갖췄다"고 써놓고 화면에는
  아무 표시가 없었다.
- **약한 저항은 표시하지 않는다.** 경기병(갑주 2 / 산개 20%)은 아무 표식이 없다.
  결정을 바꾸지 않는 수치까지 표시하면 화면이 노이즈가 된다.
- **표식 반지름은 층을 나눠 서로 겹치지 않게 둔다** (갑주 1.12r → 산개 1.16~1.3r →
  감속 1.42r → 중독 1.56r). 예전에는 산개 오라가 1.32r로 실루엣보다 훨씬 커서
  **옆 적까지 침범해** 몇 마리인지 안 읽혔고, 갑주·산개가 동시에 켜지는 충차·보스는
  링이 두 겹으로 보였다.
- **우측 패널의 웨이브 미리보기는 보드와 같은 그림·같은 실루엣을 쓴다**
  (`render/art.ts` + `render/shapes.ts`). 미리보기가 곧 범례가 되도록 하기
  위함이며, 둘이 갈라지면 형태를 신뢰할 수 없게 된다. 건설 메뉴의 타워 배지도
  같은 이유로 보드에 서는 건물 그림을 그대로 축소해서 쓴다.

### 5.5 벡터 아트 — 도형에서 그림으로

초기 빌드는 모든 것이 기하 도형이었다. 타워는 색칠한 둥근 사각형, 적은 원과
마름모, 성은 글자 라벨이었다. 형태 규칙은 성립했지만 **무엇을 지키는 게임인지가
화면에 없었다.** 그래서 `render/art.ts`에 손으로 쓴 SVG 패스 데이터를 두고
`Path2D`로 그린다.

외부 에셋을 쓰지 않은 것은 취향이 아니라 제약이다. 이 개발 환경의 네트워크
정책상 에셋 사이트에 닿지 못한다 (kenney.nl은 프록시가 403으로 막고,
opengameart.org·itch.io는 아예 연결되지 않는다). 다만 결과적으로 이득이 있었다:

- 에셋 파일도 로딩도 없어 **아티팩트 하나로 통째로 배포**해도 자체 완결이다
- 해상도에 무관하게 선명하다
- `@color`/`@accent` 토큰으로 **같은 그림에 데이터의 색을 입힌다** — 타워 색을
  `data/towers.ts`에서 바꾸면 그림이 따라온다

수록 목록: 기물 7종, 무기 5종, 적 12종 + 보스 8종, 성, 적진, 바위, 소나무.
모두 32×32 좌표계이고 건물은 바닥(y≈29) 기준, 적과 무기는 중심 기준이다.

**적을 그림으로 바꾸면서도 실루엣 규칙은 버리지 않았다.** 각 적의 외곽이 원래
도형 계열로 읽히도록 그렸고(둥근 졸병 / 앞으로 쏠린 척후 / 각진 갑병 /
위아래로 뾰족한 별동대 / 지붕 덮은 충차 / 가시 돋은 보스), 그림 **뒤에 같은 도형을
어두운 한 겹으로 깔았다.** 이 한 겹이 형태 정보를 보존하는 동시에 어두운 지형
위에서 적을 떠오르게 하는 아웃라인 역할을 겸한다. 갑주 표식도 예전에는 본체
안쪽에 그렸지만 그림을 덮어 버려서 바깥 테두리로 옮겼다.

시점은 타워·적 모두 위에서 살짝 내려다보는 측면(3/4)이다. 정확한 탑다운으로
건물을 그리면 지붕만 보여 무엇인지 알 수 없고, 적도 마찬가지다. 적은 진행
방향을 보도록 좌우로 뒤집는다(회전이 아니다 — 회전시키면 거꾸로 선다).

### 5.5.1 명암은 그림이 아니라 렌더러가 준다

패스 데이터는 **평평한 단색 면만** 칠한다. 형태는 그것으로 충분히 읽혔지만
전부 색종이를 오려 붙인 것처럼 보였다 — 나무도 돌도 천도 같은 재질이었다.

명암 레이어를 그림마다 손으로 넣는 방법도 있었지만 택하지 않았다. 그림이
40개 가까이 되는데, 그렇게 하면 **모양을 고칠 때마다 명암도 같이 고쳐야
한다.** 실제로 이 프로젝트에서 아트는 여러 번 갈아엎였다(도형 → 중세 →
한국 민속 → 조선의 전쟁). 손으로 넣은 명암은 그때마다 전부 버려졌을 것이다.

그래서 `drawArt`가 완성된 그림 위에 세 겹을 얹는다.

1. **위에서 내려오는 빛** — 위는 밝고 아래로 갈수록 어두워지는 세로 그라디언트
2. **빗면** — 왼쪽 위 모서리에 하이라이트, 오른쪽 아래 모서리에 그늘
3. **표면 결** — 미세한 잡음. 큰 면이 깨지면서 매끈한 플라스틱이 아니게 된다

**광원은 왼쪽 위 하나로 고정한다.** 그림마다 빛이 다르면 한 화면에 있는
것들이 같은 공간에 있는 것처럼 보이지 않는다.

모서리 띠는 `원본 − (원본을 한 칸 민 것)`으로 뽑는다. 패스를 직접 다루지 않고
합성으로 처리하는 이유는, **선으로 그린 부분(팔·꼬리·금줄)에도 똑같이
걸리기 때문**이다. 패스 단위로 처리했다면 선은 명암에서 빠져 혼자 평평했을
것이다. 표면 결도 같은 이유로 실루엣에 먼저 오려낸 뒤 얹는다 — 그냥 깔면
그림 바깥의 빈 화면까지 지저분해진다.

결과는 `(그림 × 크기 × 색)` 단위로 캐시한다. 적 한 마리를 매 프레임 오프스크린
네 장으로 합성할 수는 없다. 아트가 정적이라 무효화는 필요 없고, 크기는 0.5
단위로 묶는다(바위·나무는 크기를 난수로 흔들어 뽑아서 그대로 두면 캐시 항목이
무한히 늘어난다). 이 상태로 3배속 혼전에서 60fps가 유지되는 것을 확인했다.

**길에도 같은 결을 얹는다.** 바위·나무에만 재질감이 생기니 길만 매끈해서,
길 위에 물건이 놓인 게 아니라 **물건을 오려 붙인 것**처럼 보였다. 바닥과
물건이 같은 세계에 있으려면 같은 재질 처리를 받아야 한다.

### 5.6 아직 안 한 것

- **색상 팔레트는 여전히 임의로 골랐다.** 실루엣이 생겨 색 의존도는 크게 낮아졌지만,
  팔레트 자체를 색각 시뮬레이터로 검증한 적은 없다.
- **애니메이션은 날갯짓·피격 플래시·무기 흔들림뿐이다.** 걷기·사망 모션 없음.
  적 아트가 정지 포즈 하나라 이동 중에도 다리가 움직이지 않는다.
- **지형은 여전히 절차적으로 칠한다.** 잔디·흙길·자갈은 시드 난수로 흩뿌리는
  방식이고, 아트 파일에 들어 있는 건 바위와 나무뿐이다.

## 6. 아키텍처

```
src/
├─ core/          엔진 계층 — 게임 규칙을 전혀 모른다
│  ├─ loop.ts     고정 타임스텝 루프 (1/60초 고정 + 배속)
│  ├─ vec2.ts     벡터 연산
│  └─ rng.ts      시드 난수 (재현 가능한 테스트용)
│
├─ data/          밸런스 데이터 — 코드가 아니라 설정으로 취급
│  ├─ towers.ts   타워 5종 × 3레벨 수치
│  ├─ enemies.ts  적 12종 + 보스 8종 스탯
│  ├─ waves.ts    웨이브 타입과 헬퍼
│  ├─ stages.ts   스테이지 6개 (맵 + 웨이브 + 해금 보상)
│  └─ levels.ts   맵 기하 (경로 배열, 장애물)
│
├─ game/          시뮬레이션 — 렌더링을 전혀 모른다
│  ├─ Game.ts     상태 소유 + 명령 진입점 (건설/업그레이드/판매/웨이브 호출)
│  ├─ Grid.ts     타일 격자, 건설 가능 판정
│  ├─ Path.ts     경로 (진행도 → 좌표)
│  ├─ Enemy.ts    적 개체 + 데미지 계산
│  ├─ Tower.ts    타워 개체 + 타겟 선정 + 발사
│  ├─ Projectile.ts
│  ├─ WaveManager.ts  스폰 스케줄러
│  ├─ Progress.ts 클리어·해금 진행도 (저장소 주입식)
│  └─ Effects.ts  순수 연출 (로직에 영향 없음)
│
├─ render/        그리기 전용 — 상태를 읽기만 한다
│  ├─ Renderer.ts 보드(지형·타워·적·투사체·위험 오버레이)
│  ├─ art.ts      SVG 패스 벡터 아트 (타워·무기·적·성·지형지물)
│  ├─ shapes.ts   적 실루엣 — 방어 유형을 형태로 나른다
│  └─ palette.ts  색 팔레트·폰트
├─ ui/            HUD·타이틀·스테이지 선택·레이아웃·입력 히트 테스트
└─ sim/           헤드리스 밸런스 검증 — Game만 쓰고 DOM을 모른다
```

### 지켜야 하는 경계 4가지

1. **상태 변경은 반드시 `Game`의 명령 메서드를 통한다.**
   렌더러와 UI는 읽기 전용. 이 경계가 있어야 나중에 리플레이·세이브·멀티플레이를
   붙일 때 손댈 곳이 `Game.ts` 하나로 좁혀진다.

2. **밸런스 수치는 `src/data/`에만 있다.**
   `src/game/` 안에 상수 리터럴이 나타나면 잘못된 것이다. 데이터와 로직을 분리해야
   밸런스 조정이 코드 리뷰 없이 가능하고, 나중에 JSON/스프레드시트로 뽑아낼 수 있다.

3. **시뮬레이션은 고정 타임스텝, 렌더링만 가변.**
   1/60초 단위로만 시뮬레이션을 돌리므로 60Hz든 144Hz든 밸런스가 같다.
   배속은 한 프레임에 스텝을 여러 번 도는 방식이라 정확도가 유지된다.

4. **연출용 난수는 시뮬레이션 난수와 다른 스트림을 쓴다** (`Game.cosmeticRng`).
   같은 스트림에서 그림용 값을 하나만 뽑아도 이후 모든 시뮬레이션 난수가 한 칸씩
   밀린다. 실제로 적을 길 폭 안에서 좌우로 흩뿌리는 **순수 렌더링 변경**을 넣었더니
   임계값 근처 전략의 클리어율이 20%→60%로 흔들렸다. 게임 규칙은 하나도 안 건드렸는데
   측정값이 바뀌면 시뮬레이터를 밸런스 계측기로 신뢰할 수 없다.
   같은 이유로 좌우 흩뿌림은 `pos`가 아니라 렌더러에서만 적용한다 — `pos`를 옮기면
   타워 사거리 판정이 실제로 바뀐다.

### 핵심 설계 판단: 적의 위치를 스칼라 하나로 표현

적은 `(x, y)`가 아니라 **경로를 따라 얼마나 왔는가(`distance`)** 를 상태로 갖고,
픽셀 좌표는 매 스텝 `Path.positionAt(distance)`로 파생시킨다. 적은 자기 경로를 직접
들고 있어서, 맵에 경로가 여러 개여도 호출부가 "이 적이 어느 길인가"를 신경 쓸 필요가 없다.
이 하나의 결정이 아래를 전부 공짜로 만든다:

- 선두/후미 타겟팅 = 남은 거리(`remaining`) 비교 한 번 — 경로 길이가 서로 달라도 의미가 같다
- 감속 = 스칼라 곱
- 화차의 예측 사격 = `positionAt(distance + speed × 비행시간)`
- 경로 이탈·되돌아감 같은 버그가 원천적으로 불가능

## 7. 조작

| 입력 | 동작 |
|---|---|
| `1`~`5` | 타워 선택 (해금된 것만, 메뉴 순서와 일치) |
| 좌클릭 (빈 땅) | 선택한 타워 건설 |
| 좌클릭 (타워) | 타워 선택 → 우측 패널에 상세·업그레이드·판매 |
| 우클릭 / `Esc` | 건설 모드 및 선택 해제 |
| `Space` | 다음 웨이브 조기 소환 |
| `U` / `X` / `T` | 선택 타워 업그레이드 / 판매 / 타겟팅 변경 |
| `P` | 일시정지 |
| `R` | 스테이지 다시 시작 |
| `Q` | 스테이지 선택 화면으로 |
| 상단 `1x` `2x` `3x` | 배속 |
| 타이틀에서 `1`~`3` | 난이도 선택 · `Enter`/`Space` 시작 |

**결과 화면에서는 다음 행동을 버튼으로 제시한다** — `다음 스테이지 ▶` / `다시 하기` /
`스테이지 선택`. 예전에는 우측 패널 구석의 "다시 시작" 하나뿐이었고 다음 판으로 가는
길은 `Q` 키를 아는 사람만 쓸 수 있었다. 한 판을 깬 직후는 **다음 행동이 화면에 있어야
하는 순간**이라 결과 카드 바로 아래에 놓는다.

## 8. UX 원칙

- **정보를 미리 준다.** 준비 단계에서 다음 웨이브의 구성과 위협 태그(기마/갑주/산개/고속)를
  패널에 항상 표시한다. 상성 게임에서 정보를 숨기면 "시행착오 게임"이 되고 재미가 죽는다.
- **실패 사유를 말한다.** 건설이 막히면 "골드가 40 부족합니다" 같은 구체적 사유를 돌려준다
  (`BuildResult`).
- **적의 방어를 형태로 구분할 수 있다.** 실루엣이 방어 유형을, 날개가 기마 여부를
  나른다. 색은 보조 수단일 뿐이다 — 자세한 규칙은 5장.
- **되돌릴 수 있다.** 판매 70% 환급으로 빌드 실수를 회복할 수 있게 한다.
- **보상은 이름이 아니라 그림과 수치로 보여준다.** 스테이지 클리어 화면의 해금 카드는
  타워 그림 + 한 줄 정체성 + 실제 수치(가격·타입·특수효과) + 왜 필요한가를 함께 싣는다.
  새 기물이 열렸다는 사실보다 **"이걸로 무엇이 달라지는가"** 가 다음 스테이지의 판단을
  바꾸기 때문이다. 이름만 작게 적던 시절에는 해금이 그냥 지나갔다.
- **버튼의 그림과 클릭 영역은 한 곳에서 만든다.** 결과 화면 버튼도 Renderer가 아니라
  `Hud`가 그린다 — 히트 영역을 만드는 쪽이 그리기도 해야 둘이 어긋날 수 없다.
  대신 Renderer가 카드 묶음의 아래쪽 y를 돌려주어 버튼이 카드를 덮지 않게 한다
  (양쪽에서 같은 산수를 따로 했더니 실제로 겹쳤다).

## 9. 밸런스 검증 상태

전체 결과와 방법론은 [`BALANCE.md`](BALANCE.md)에 있다. 요약:

| 질문 | 답 |
|---|---|
| 각 스테이지가 그때 가진 기물로 풀리는가? | **풀린다.** 적응형 빌드가 S1~S6 전부 95~100% |
| 몰빵 빌드는 막히는가? | **막힌다.** S2 이후 전 스테이지 0~10% |
| 해금이 실제로 필요한가? | **총통·거마작은 확인됨** (S2 사수 0% vs 총통 100%, S5 거마작 10% vs 50%). **별파진·불랑기는 미검증** |
| 보스가 밸런스를 깨뜨리는가? | 아니다. 1,300판 재검증에서 몰빵 차단·해금 필요성이 모두 유지됨 (S4 총통 몰빵만 10%로 새어 나감) |
| 어려움(125%)이 클리어 가능한가? | **조기 소환을 챙기는 빌드만** 가능 (S5 60%). 일반 빌드는 S2부터 무너진다 |
| 경로 수가 난이도에 영향을 주는가? | **크게 준다.** 2·3갈래 맵은 압박을 절반 이하로 낮춰야 같은 체감 |
| 조기 소환 2G/초가 과한가? | 아니다. 클리어 여부를 뒤집지 않고 남은 생명만 올린다 |
| 거마작이 픽되는가? | **기마 웨이브에서는 픽된다.** 다만 딜 편중 AI 기준으로는 여전히 "없어도 되는" 스테이지가 있다 |
| 업그레이드가 신규 건설과 경쟁되는가? | 초반만. "키우기"(6기 만렙)는 S1~S4 100%지만 S5·S6에서 0% |

**아직 열려 있는 것**

- [ ] **별파진의 필수성** — S5는 독 없이도 클리어된다. 해금 보상 중 유일하게 미검증
- [ ] 화차 기마 페널티 — "징 + 사수" 지상 편중 조합 대조군이 필요
- [ ] S1이 완전 무손실 — 튜토리얼로는 맞지만 생명 시스템을 한 번도 못 배운다
- [ ] "키우기" 빌드가 여전히 열세
- [ ] 타겟팅 우선순위 축 미검증
- [ ] 색상 팔레트의 색각 시뮬레이터 검증

**밸런스 데이터를 고쳤다면 반드시 `npm run sim -- --runs 20`을 다시 돌리고
`BALANCE.md` 5장 표를 갱신할 것.**
