# 게임 설계 문서 (GDD) — 밤길 방어전

> 경로형 타워디펜스. 이 문서는 "왜 이렇게 만들었는가"를 남기는 곳이고,
> 실제 수치는 `src/data/` 아래 파일이 단일 진실 공급원(single source of truth)이다.
> 수치를 바꿀 때는 데이터 파일을 고치고, 의도가 바뀌면 이 문서를 고친다.

---

## 1. 한 줄 요약

정해진 경로를 따라 밀려오는 20개 웨이브의 적을, 길 옆 빈 땅에 타워를 지어 막는다.
**"어떤 타워를 짓느냐"가 아니라 "어떤 조합을 어디에 짓느냐"** 가 승패를 가른다.

## 2. 참고한 게임과 각각에서 가져온 것

| 게임 | 가져온 설계 | 이 프로젝트에서의 구현 |
|---|---|---|
| **Kingdom Rush** | 소수의 타워 아키타입 + 명확한 상성. 타워 4종만으로 깊이를 만든다 | 장승·서낭당·징·솟대 4종. 각자 "절대 못 하는 것"을 하나씩 부여 |
| **Kingdom Rush** | 웨이브 사이 준비 시간 + 조기 소환 보너스 | `prepTime` 카운트다운, 남은 시간 × 2G 보너스 |
| **Bloons TD 6** | 타겟팅 우선순위(First/Last/Strong/Close)를 플레이어가 지정 | 타워별 `targetPriority`, 패널에서 순환 전환 |
| **Bloons TD 6** | 적의 "속성"(납·위장 등)이 특정 타워를 무력화 | 장갑 / 마법저항 / 공중 3축 방어 스탯 |
| **Plants vs. Zombies** | 새 위협을 한 번에 하나씩, 경고와 함께 도입 | 웨이브 `warning` 필드, 4·6·7·10·12·14웨이브에서 신규 위협 |
| **Dungeon Defenders** | 판매 환급으로 빌드 교체를 허용 (실수 회복 가능) | 투자 골드의 70% 환급 |
| **Defense Grid** | 유출(leak) 시 즉사가 아니라 생명 차감 → 실패해도 계속 플레이 | 생명 20, 적 종류별 `leak` 값 (보스는 10) |

**의도적으로 빼기로 한 것**

- **미로 짓기(BTD/Desktop TD식 경로 변경)** — 경로가 고정이라 A* 재계산·경로 봉쇄 검증이 필요 없다.
  최적해가 "미로 최대화" 하나로 수렴해 타워 조합의 의미가 줄어드는 문제도 피한다.
- **영웅 유닛 / 병영 유닛** — 이동·교전 AI가 필요해 코어 규모를 크게 키운다. 로드맵 2단계로 미룸.
- **특수기(운석·증원 등 쿨다운 액티브)** — 코어 검증 뒤 추가. 로드맵 1단계.

## 3. 핵심 루프

```
준비 (prepTime 초)
  ├─ 다음 웨이브 구성을 패널에서 확인
  ├─ 골드로 타워 건설 / 업그레이드 / 판매
  └─ [다음 웨이브] 조기 소환 → 남은 초 × 2G 보너스
        ↓
교전
  ├─ 적이 경로를 따라 진행, 타워가 자동 사격
  ├─ 처치 → 즉시 현상금 골드
  └─ 완주 → 생명 차감
        ↓
클리어 보상 골드 → 다시 준비
        ↓
20웨이브 클리어 = 승리 / 생명 0 = 패배
```

**플레이어가 매 웨이브 내리는 결정 3가지**

1. **넓히기 vs 키우기** — 새 타워를 지을까, 기존 타워를 업그레이드할까
   (업그레이드는 골드 대비 DPS가 좋고, 신규 건설은 커버리지가 넓어진다)
2. **조합 맞추기** — 다음 웨이브의 방어 속성에 맞는 타워가 사거리 안에 있는가
3. **지금 부를까** — 조기 소환 보너스를 먹을 만큼 방어선이 준비됐는가

## 4. 밸런스의 축

### 4.1 데미지 타입 × 방어 스탯

이 게임의 모든 상성은 아래 두 줄에서 나온다 (`src/game/Enemy.ts`의 `takeDamage`).

```
물리 데미지 = max(1, 공격력 − 장갑)          ← 고정 감소. 저데미지·고연사 타워가 크게 손해
마법 데미지 = max(1, 공격력 × (1 − 마법저항))  ← 비율 감소. 고데미지 타워도 똑같이 손해
```

**고정 감소 vs 비율 감소를 일부러 다르게 잡은 이유:**
장갑은 "한 방이 약한 타워"를 죽인다 (장승 L3 24딜 vs 석장승의 넋 장갑 18 → 6딜, **−75%**).
마법저항은 "한 방이 센 타워"도 똑같이 죽인다 (서낭당 L3 94딜 vs 손각시 마저 80% → 18.8딜, **−80%**).
두 방어가 서로 다른 방식으로 아프기 때문에, 한쪽 타워만 도배하면 반드시 벽에 부딪힌다.

이 전제는 **장승이 실제로 저데미지일 때만** 성립한다. 초기 수치에서는 장승 L3 데미지가
36으로 서낭당 L1(32)보다 높아 전제 자체가 깨져 있었고, 시뮬레이션에서 장승 몰빵이 무손실
클리어했다. 자세한 경위는 [`BALANCE.md`](BALANCE.md) 3장.

### 4.2 4개 타워의 역할

| 타워 | 타입 | 공중 | 특징 | 카운터당하는 적 |
|---|---|---|---|---|
| 장승 70G | 물리 | ○ | 골드 대비 DPS 1위, 저데미지 고연사 (L3 24×2.7) | 귀졸(장갑 12), 석장승의 넋(장갑 18) |
| 서낭당 110G | 마법 | ○ | 장갑 완전 무시, 느리고 비쌈 (L3 94×1.05) | 원귀(65%), 손각시(80%) |
| 굿청 징 130G | 물리·광역 | **✕** | 지상 물량 정리 최강, 발사 매우 느림 | 모든 공중 유닛 |
| 금줄 솟대 75G | 마법·광역 | ○ | 딜 거의 없음(L3 8), 범위 감속 −78% / 7초 | (직접 카운터 없음 — 서포터) |
| 팥 항아리 100G | **순수** | ○ | 직접 딜 거의 없음, 중독 28/s × 4초. 장갑도 마법저항도 통과 | (직접 카운터 없음 — 탱커 해답) |

**금줄 솟대를 넣은 이유**: 나머지 3개는 전부 "직접 딜"이라 선택이 단순한 상성 퀴즈가 된다.
금줄 솟대는 자기 DPS가 아니라 *다른 타워의 유효 사격 시간*을 늘리는 곱셈 축이라,
"어디에 놓을 것인가"라는 위치 판단 문제를 게임에 추가한다. 코너 안쪽에 놓으면
적이 감속된 채로 여러 타워의 사거리를 통과하게 만들 수 있다.

**상태 이상은 중첩되지 않는다** — 감속도 중독도 가장 강한 것 하나만 적용하고 지속시간만
갱신한다 (`Enemy.applySlow` / `applyPoison`). 서포터 타워를 도배해 적을 정지시키거나
녹여버리는 퇴화 전략을 막기 위함이며, 그래서 두 타워 모두 1~2기가 최적이고 과투자는 손해다.

**감속 지속시간이 사거리보다 중요하다.** 지속이 짧으면 적이 금줄 솟대 사거리를 벗어나는 순간
감속이 풀려 뒤쪽 타워가 아무 이득을 못 본다. 서포터가 성립하려면 감속이 **타워를 지나간 뒤에도
남아야** 한다 — 검증 과정에서 지속을 2.2초 → 7초로 늘리고 나서야 금줄 솟대가 값을 하기 시작했다
([`BALANCE.md`](BALANCE.md) 4장).

### 4.3.1 보스

**스테이지 중간과 끝에 보스를 둔다.** 웨이브 하나를 "물량"이 아니라 "한 덩어리"로
바꿔 리듬을 끊는 장치다. 물량 웨이브는 커버리지로 풀지만 보스는 **집중 화력과 상성**으로
풀어야 해서, 같은 스테이지 안에서 서로 다른 질문을 던진다.

| 보스 | HP | 장갑 | 마저 | 정체성 | 등장 |
|---|---|---|---|---|---|
| 도깨비 대감 | 1250 | 0 | 0 | 방어 없는 덩치 — 순수 화력 시험 | S1 W8 |
| 두억시니 | 2300 | **22** | 0 | 물리 완전 무력화 → 서낭당 강제 | S2 W10, S4 W8, S5 W14 |
| 삼두구미 | 1900 | 5 | 25% | **공중** — 징 조준 불가 + 빠름 | S3 W7, S5 W8 |
| 구미호 | 2100 | 0 | **78%** | 서낭당 몰빵 응징 → 물리 강제 | S3 W12 |
| 그슨대 | 4400 | **18** | **52%** | 양면 저항 — 한쪽 화력으로는 못 녹인다 | S4 W14 |
| 저승사자 | 5200 | 14 | 45% | 최종 보스 | S5 W20 |

**보스도 실루엣 규칙을 따른다.** 전부 `boss`(가시 다각)를 쓰되 방어 표식이 스탯에서
파생되므로 장갑 보스에는 흰 테두리가, 마법저항 보스에는 보라 오라가 자동으로 뜬다.
형태만 보고 "무엇으로 때려야 하는가"가 여전히 읽힌다.

**중간 보스와 최종 보스의 leak을 다르게 잡았다.** 중간 보스는 2~4, 최종 보스는 10.
검증 과정에서 중간 보스 leak을 4~6으로 두자 S5가 **모든 전략 0%** 가 됐다 — 중간에
두 번 뚫리는 것만으로 생명 풀이 바닥나 최종 웨이브를 볼 수 없었다. 중간 보스는
"뚫리면 아프지만 판은 이어지는" 체크포인트여야 한다.

**보스를 넣을 때는 그 웨이브의 잡몹을 줄인다.** 처음에는 35~40%를 덜어냈는데,
S4에서 고속 물량이 사라지자 **서낭당 몰빵이 100% 클리어**해 버렸다 (금줄 솟대 해금의
필요성을 증명하던 지점이 무너졌다). 잡몹은 5~10%만 덜고 보스를 얹는 쪽이 옳다.

### 4.4 난이도 곡선 (20 웨이브)

| 구간 | 주제 | 플레이어가 배워야 하는 것 |
|---|---|---|
| 1–5 | 기본기 | 경로 커버리지, 골드 운용. 장승만으로 넘어간다 |
| 6–10 | 방어 도입 | 장갑↔마법 / 마저↔물리 / 공중↔징 상성 |
| 11–15 | 복합 | 상성이 반대인 적을 같은 웨이브에 섞음. 단일 빌드가 여기서 무너진다 |
| 16–20 | 총력전 | 물량+저항+공중 동시 압박, 마지막에 보스 |

**경제 튜닝** — 스테이지마다 골드가 0부터 다시 시작한다. 시작 골드는 270~520G,
수입은 처치 현상금 + 웨이브 클리어 보상 + 조기 소환 보너스로 들어온다.

경제는 이 게임에서 가장 민감한 축이다. 단일 20웨이브 시절에는 총 수입이 필요액의 2.5배여서
모든 몰빵 빌드가 무손실 클리어했고, 스테이지로 나눈 뒤에는 반대로 초반 골드가 말라
S2~S5가 전멸했다. 수치를 고칠 때는 `npm run sim -- --audit`으로 스테이지별 수입 곡선을
먼저 확인하고, `--income` / `--hp` 배율로 스윕한 뒤 확정값만 데이터에 반영할 것.

### 4.5 스테이지와 해금

게임은 스테이지 5개로 나뉘고, **하나를 깰 때마다 기물 1종이 열린다.** 선형 해금이라
앞 스테이지를 깨야 다음이 열린다.

| 스테이지 | 맵 | 경로 | 웨이브 | 시작 시 보유 | 클리어 보상 |
|---|---|---|---|---|---|
| S1 마을 어귀 | 완만한 S자 | 1 | 8 | 장승 | **서낭당** |
| S2 무너진 돌담 | 촘촘한 지그재그 | 1 | 10 | 장승·서낭당 | **굿청 징** |
| S3 갈림길 서낭 | 두 출발점이 합류 | **2** | 12 | +징 | **금줄 솟대** |
| S4 안개 고개 | 길게 되접히는 나선 | 1 | 14 | +솟대 | **팥 항아리** |
| S5 저승 문턱 | 세 방향 동시 압박 | **3** | 20 | 전부 | — (최종) |

**설계 규칙: 새로 열린 기물은 다음 스테이지에서 곧바로 필요해야 한다.** 그러지 않으면
해금은 그냥 숫자가 늘어나는 일이 되고 배우는 게 없다. 그래서 각 스테이지의 신규 위협은
직전 보상이 답이 되도록 배치했다 — S2의 귀졸에는 서낭당, S3의 도깨비불에는 징이
아닌 것, S4의 고속 물량에는 금줄 솟대.

이 규칙이 실제로 성립하는지가 밸런스 검증의 핵심 질문이고, S4에서는 명확히 확인됐다
(금줄 솟대 0기 0% vs 1기 100%). 반면 S5의 팥 항아리는 아직 필수성이 검증되지 않았다 —
[`BALANCE.md`](BALANCE.md) 6장 참고.

**진행도는 localStorage에 저장된다** (`game/Progress.ts`). 저장소를 주입받는 구조라
헤드리스 시뮬레이터와 테스트는 메모리 저장소를 쓴다.

### 4.6 난이도 — 바뀌는 축은 하나뿐

| 난이도 | 적 체력 | 검증 |
|---|---|---|
| 쉬움 | 70% | 조합 빌드 전 스테이지 100% (S5 생명 5.0) |
| 보통 | 100% | 기준. 아래 9장의 표가 전부 이 값 |
| 어려움 | 125% | **조기 소환으로 경제를 굴리는 빌드만** 전 스테이지 클리어 (S5 60%) |

**웨이브 구성·적 종류·타워 수치는 난이도와 무관하게 동일하다.** 이유가 둘이다.

1. 이 게임의 설계는 "어떤 조합으로 어떤 상성을 푸는가"에 있다. 난이도가 적 종류나
   방어 스탯을 바꾸면 **풀이 자체가 달라져** 쉬움에서 배운 것이 어려움에서 통하지 않는다.
2. 검증 비용. 축이 하나(체력 배율)뿐이면 다른 난이도를 배율 스윕으로 읽어낼 수 있다.
   난이도마다 웨이브가 다르면 1,300판 검증을 난이도 수만큼 다시 해야 한다.

**어려움 배율은 스윕으로 정했다.** 처음 잡은 145%는 시뮬레이터 AI 기준 S2부터 전멸했다 —
적을 못 잡으면 현상금이 안 들어오고, 그러면 타워를 못 짓고, 다시 더 못 잡는 **경제
죽음의 나선**이다. 1.10 / 1.15 / 1.20 / 1.25를 스윕해 보니 일반 빌드는 1.15부터
무너지지만 조기 소환 보너스를 챙기는 빌드는 1.25까지 전 스테이지를 클리어했다.
그래서 어려움은 "화력이 아니라 **경제 운용**을 요구하는 난이도"로 정의된다.

**해금은 난이도와 무관하게 공유한다.** 쉬움으로 깬 사람도 다음 스테이지와 기물이
열린다 — 난이도는 진입 장벽이지 콘텐츠 잠금이 아니다. 다만 최고 기록은
`스테이지ID@난이도ID`로 따로 남긴다. 쉬움의 20과 어려움의 3을 같은 칸에 적으면
기록이 아무 의미가 없어진다.

**경로 수가 난이도를 크게 좌우한다.** 경로가 갈라지면 타워 커버리지가 그만큼 나뉘어,
같은 압박 수치라도 2갈래 맵은 1갈래보다 훨씬 어렵다. 맵을 추가할 때는 경로 수에 맞춰
압박을 다시 잡아야 한다.

## 5. 시각 언어 (아트 디렉션)

### 5.1 세계관: 달밤의 귀신 행렬 (한국 민속) — 왜 이걸 골랐나

**처음에는 중세 판타지였다.** 근거도 있었다 — 상성이 "물리 − 장갑"과
"마법 × (1 − 마법저항)" 두 줄에서 나오니, "갑옷은 화살을 막지만 마법은 못 막는다"가
설명 없이 통하는 장르를 고르는 게 학습 비용상 유리하다는 것이었다. 틀린 말은
아니지만, 그 조건을 만족하는 장르가 중세 판타지 하나뿐이라는 전제가 틀렸다.

**한국 민속은 같은 이분법을 더 강하게 갖고 있다.** 벽사(辟邪)는 원래 두 갈래다.

| 밸런스 축 | 중세 판타지 | 한국 민속 |
|---|---|---|
| 물리 | 화살 · 포탄 | 복숭아나무 화살 · 징 소리 |
| 마법 | 마법 투사체 | **부적** — 괴황지에 경면주사로 쓴 글자 |
| 장갑 | 판금 갑옷 | **두정갑** — 귀졸이 입은 것 |
| 마법저항 | 마법 저항 로브 | **원한** — 한이 깊을수록 부적이 안 듣는다 |
| 방어 무시 | 독 | **팥** — 잡귀는 종류를 가리지 않고 팥을 못 넘는다 |

"원한이 깊으면 부적이 안 먹힌다"는 마법저항보다 오히려 직관적이고, 팥이 모든
잡귀에게 통한다는 전승은 순수 피해라는 개념과 정확히 겹친다. 학습 비용이 문제라면
이쪽이 더 싸다.

**그리고 중세는 진부했다.** 타워디펜스에서 고블린과 궁수탑은 기본값이라 아무것도
말하지 않는다. 장승·서낭당·솟대는 같은 역할을 하면서 화면을 처음 보는 사람에게
"이건 무엇인가"를 만든다.

**교체 비용이 거의 0이었다는 것도 판단 근거였다.** 아트가 `render/art.ts` 한
파일에 모여 있고 수치는 `data/`에 따로 있어, 세계관을 바꿔도 밸런스는 한 줄도
건드리지 않는다. 실제로 교체 후 1,300판 시뮬레이션 결과가 **완전히 동일**했다 —
이름과 그림만 바뀌었다는 증거다.

**고증 방침.** 자료로 확인한 것과 추정한 것을 `render/art.ts` 머리말에 나눠
적어 뒀다. 대표적으로 저승사자의 검은 갓 + 하얀 얼굴은 옛 기록이 아니라 1970년대
「전설의 고향」이 만든 이미지인데, 한국 사람이 한 번에 알아보는 형태가 이것뿐이라
**고증보다 가독성을 택했다**고 명시했다. 반대로 도깨비의 뿔은 일본 오니의
이미지가 섞인 것이라 **일부러 뺐다** — 이쪽은 빼도 도깨비로 읽히기 때문이다.
기준은 "고증이 가독성을 해치지 않는 한 고증을 따른다"이다.

### 5.2 원칙: 시각 속성은 테마가 아니라 규칙을 나른다

화면의 모든 형태·표식은 **게임 규칙 하나씩에 대응한다.** 멋있어 보이려고 넣은
요소는 없다. 3배속에서 40마리가 몰려올 때 "저건 굿청 징이 못 때리는 놈"이
즉시 읽히지 않으면 상성 설계 전체가 무의미해지기 때문이다.

| 화면에 보이는 것 | 나르는 규칙 |
|---|---|
| **실루엣** (아래 5.3) | 적의 방어 유형 → 어떤 타워가 필요한가 |
| **날개 + 부양 + 작고 진한 그림자** | 공중 유닛 → 굿청 징 조준 불가 |
| 본체를 감싼 같은 실루엣의 밝은 테두리 | 장갑 있음 |
| 보라 점선 오라 | 마법저항 있음 |
| 하늘색 링 | 지금 감속 걸림 |
| 연두 점선 링 | 지금 중독 — 방어 무시 피해 진행 중 |
| 기물 5종의 무기 (복숭아 화살·부적·징채·금줄 매듭·팥 표주박) | 기물 종류 |
| 타워 받침 옆 점 개수 + 건물 크기 | 타워 레벨 |
| 무기 회전 + 발사 반동 + 머즐 플래시 | 지금 누구를 겨누고 쐈는가 |
| 화면 가장자리 붉은 비네트 · 테두리 | 생명이 얼마나 위험한가 |

**위험 표시는 한 겹으로만 그린다.** 위험도 비네트와 유출 플래시가 각각 보드를
덮던 시절에는, 생명이 3일 때 보스가 유출되면 두 겹이 더해져 판이 통째로 불투명한
빨간색이 됐다 — 티는 확실히 났지만 그 0.6초 동안 플레이가 불가능했다. 지금은 두
효과의 **세기만 합치고 그림은 한 번**, 그것도 가장자리 가중으로 그린다.
판 가운데는 어떤 상황에서도 보여야 한다.

### 5.3 실루엣 = 방어 유형

**색이 아니라 형태에 정보를 싣는다.** 이유가 두 가지다.

1. 색각 이상 사용자도 "어떤 타워로 잡아야 하는가"를 판단할 수 있어야 한다.
2. 고배속에서 사람 눈은 색보다 실루엣을 먼저 읽는다.

| 실루엣 | 형태 | 의미 | 해당 적 |
|---|---|---|---|
| `basic` | 원 | 방어 없음 — 아무 타워나 통함 | 허깨비 |
| `swift` | 진행 방향 쐐기 | 고속 — 감속 없으면 체류가 짧다 | 장산범, 도깨비불 |
| `armored` | 육각 | 장갑 — 물리가 깎이니 **서낭당** | 귀졸, 석장승의 넋 |
| `warded` | 세로 마름모 | 마법저항 — 부적이 깎이니 **물리 기물** | 원귀, 손각시 |
| `bulwark` | 방패 오각 | 양면 저항 탱커 | 불가사리 |
| `boss` | 가시 다각 | 보스 | 저승사자 |

**공중 여부는 실루엣이 아니라 날개로 표현한다.** 방어 유형과 직교하는 축이기
때문이다 — 도깨비불(고속·공중)과 석장승의 넋(장갑·공중)는 실루엣이 다르고
날개를 공유한다. 날개는 본체보다 넓게 펴고 밝은 테두리로 값을 분리했다.
같은 색·같은 명도로 그렸더니 실루엣이 하나로 뭉쳐 "날고 있다"가 읽히지 않았고,
장산범(지상 쐐기)과 도깨비불(공중 쐐기)이 색으로만 구분되는 상태가 됐다.

### 5.4 지켜야 하는 규칙

- **`EnemyDef.silhouette`은 실제 스탯과 반드시 일치시킨다.** 형태가 정보를 나르는
  구조라, 여기가 어긋나면 플레이어가 화면을 보고 잘못된 타워를 짓는다.
  장갑 지배적 → `armored`, 마법저항 지배적 → `warded`, 둘 다 → `bulwark`.
- **방어 표식은 실루엣에서 파생시킨다.** 별도 임계값을 두면 실루엣과 어긋난다.
  실제로 예전에는 `magicResist >= 0.5` 하드코딩 때문에 **마저 45%인 보스에
  마법 표식이 안 떴다** — 설명문에는 "모든 방어를 갖췄다"고 써놓고 화면에는
  아무 표시가 없었다.
- **약한 저항은 표시하지 않는다.** 도깨비불(장갑 2 / 마저 20%)은 아무 표식이 없다.
  결정을 바꾸지 않는 수치까지 표시하면 화면이 노이즈가 된다.
- **표식 반지름은 층을 나눠 서로 겹치지 않게 둔다** (장갑 1.12r → 마저 1.16~1.3r →
  감속 1.42r → 중독 1.56r). 예전에는 마저 오라가 1.32r로 실루엣보다 훨씬 커서
  **옆 적까지 침범해** 몇 마리인지 안 읽혔고, 장갑·마저가 동시에 켜지는 불가사리·보스는
  링이 두 겹으로 보였다.
- **우측 패널의 웨이브 미리보기는 보드와 같은 그림·같은 실루엣을 쓴다**
  (`render/art.ts` + `render/shapes.ts`). 미리보기가 곧 범례가 되도록 하기
  위함이며, 둘이 갈라지면 형태를 신뢰할 수 없게 된다. 건설 메뉴의 타워 배지도
  같은 이유로 보드에 서는 건물 그림을 그대로 축소해서 쓴다.

### 5.5 벡터 아트 — 도형에서 그림으로

초기 빌드는 모든 것이 기하 도형이었다. 타워는 색칠한 둥근 사각형, 적은 원과
마름모, 성은 글자 라벨이었다. 형태 규칙은 성립했지만 **무엇을 지키는 게임인지가
화면에 없었다.** 그래서 `render/art.ts`에 손으로 쓴 SVG 패스 데이터를 두고
`Path2D`로 그린다.

외부 에셋을 쓰지 않은 것은 취향이 아니라 제약이다. 이 개발 환경의 네트워크
정책상 에셋 사이트에 닿지 못한다 (kenney.nl은 프록시가 403으로 막고,
opengameart.org·itch.io는 아예 연결되지 않는다). 다만 결과적으로 이득이 있었다:

- 에셋 파일도 로딩도 없어 **아티팩트 하나로 통째로 배포**해도 자체 완결이다
- 해상도에 무관하게 선명하다
- `@color`/`@accent` 토큰으로 **같은 그림에 데이터의 색을 입힌다** — 타워 색을
  `data/towers.ts`에서 바꾸면 그림이 따라온다

수록 목록: 기물 5종, 무기 5종, 적 8종 + 보스 6종, 마을, 무덤, 바위, 소나무.
모두 32×32 좌표계이고 건물은 바닥(y≈29) 기준, 적과 무기는 중심 기준이다.

**적을 그림으로 바꾸면서도 실루엣 규칙은 버리지 않았다.** 각 적의 외곽이 원래
도형 계열로 읽히도록 그렸고(둥근 허깨비 / 앞으로 쏠린 장산범 / 각진 귀졸 /
위아래로 뾰족한 소복 / 쇳조각 박힌 불가사리 / 가시 돋은 보스), 그림 **뒤에 같은 도형을
어두운 한 겹으로 깔았다.** 이 한 겹이 형태 정보를 보존하는 동시에 어두운 지형
위에서 적을 떠오르게 하는 아웃라인 역할을 겸한다. 장갑 표식도 예전에는 본체
안쪽에 그렸지만 그림을 덮어 버려서 바깥 테두리로 옮겼다.

시점은 타워·적 모두 위에서 살짝 내려다보는 측면(3/4)이다. 정확한 탑다운으로
건물을 그리면 지붕만 보여 무엇인지 알 수 없고, 적도 마찬가지다. 적은 진행
방향을 보도록 좌우로 뒤집는다(회전이 아니다 — 회전시키면 거꾸로 선다).

### 5.6 아직 안 한 것

- **색상 팔레트는 여전히 임의로 골랐다.** 실루엣이 생겨 색 의존도는 크게 낮아졌지만,
  팔레트 자체를 색각 시뮬레이터로 검증한 적은 없다.
- **애니메이션은 날갯짓·피격 플래시·무기 흔들림뿐이다.** 걷기·사망 모션 없음.
  적 아트가 정지 포즈 하나라 이동 중에도 다리가 움직이지 않는다.
- **지형은 여전히 절차적으로 칠한다.** 잔디·흙길·자갈은 시드 난수로 흩뿌리는
  방식이고, 아트 파일에 들어 있는 건 바위와 나무뿐이다.

```
│
├─ render/        그리기 전용 — 상태를 읽기만 한다
│  ├─ Renderer.ts 보드(지형·타워·적·투사체·위험 오버레이)
│  ├─ art.ts      SVG 패스 벡터 아트 (타워·무기·적·성·지형지물)
│  ├─ shapes.ts   적 실루엣 — 방어 유형을 형태로 나른다
│  └─ palette.ts  색 팔레트·폰트
├─ ui/            HUD·타이틀·스테이지 선택·레이아웃·입력 히트 테스트
└─ sim/           헤드리스 밸런스 검증 — Game만 쓰고 DOM을 모른다
```

### 지켜야 하는 경계 4가지

1. **상태 변경은 반드시 `Game`의 명령 메서드를 통한다.**
   렌더러와 UI는 읽기 전용. 이 경계가 있어야 나중에 리플레이·세이브·멀티플레이를
   붙일 때 손댈 곳이 `Game.ts` 하나로 좁혀진다.

2. **밸런스 수치는 `src/data/`에만 있다.**
   `src/game/` 안에 상수 리터럴이 나타나면 잘못된 것이다. 데이터와 로직을 분리해야
   밸런스 조정이 코드 리뷰 없이 가능하고, 나중에 JSON/스프레드시트로 뽑아낼 수 있다.

3. **시뮬레이션은 고정 타임스텝, 렌더링만 가변.**
   1/60초 단위로만 시뮬레이션을 돌리므로 60Hz든 144Hz든 밸런스가 같다.
   배속은 한 프레임에 스텝을 여러 번 도는 방식이라 정확도가 유지된다.

4. **연출용 난수는 시뮬레이션 난수와 다른 스트림을 쓴다** (`Game.cosmeticRng`).
   같은 스트림에서 그림용 값을 하나만 뽑아도 이후 모든 시뮬레이션 난수가 한 칸씩
   밀린다. 실제로 적을 길 폭 안에서 좌우로 흩뿌리는 **순수 렌더링 변경**을 넣었더니
   임계값 근처 전략의 클리어율이 20%→60%로 흔들렸다. 게임 규칙은 하나도 안 건드렸는데
   측정값이 바뀌면 시뮬레이터를 밸런스 계측기로 신뢰할 수 없다.
   같은 이유로 좌우 흩뿌림은 `pos`가 아니라 렌더러에서만 적용한다 — `pos`를 옮기면
   타워 사거리 판정이 실제로 바뀐다.

### 핵심 설계 판단: 적의 위치를 스칼라 하나로 표현

적은 `(x, y)`가 아니라 **경로를 따라 얼마나 왔는가(`distance`)** 를 상태로 갖고,
픽셀 좌표는 매 스텝 `Path.positionAt(distance)`로 파생시킨다. 적은 자기 경로를 직접
들고 있어서, 맵에 경로가 여러 개여도 호출부가 "이 적이 어느 길인가"를 신경 쓸 필요가 없다.
이 하나의 결정이 아래를 전부 공짜로 만든다:

- 선두/후미 타겟팅 = 남은 거리(`remaining`) 비교 한 번 — 경로 길이가 서로 달라도 의미가 같다
- 감속 = 스칼라 곱
- 굿청 징의 예측 사격 = `positionAt(distance + speed × 비행시간)`
- 경로 이탈·되돌아감 같은 버그가 원천적으로 불가능

## 7. 조작

| 입력 | 동작 |
|---|---|
| `1`~`5` | 타워 선택 (해금된 것만, 메뉴 순서와 일치) |
| 좌클릭 (빈 땅) | 선택한 타워 건설 |
| 좌클릭 (타워) | 타워 선택 → 우측 패널에 상세·업그레이드·판매 |
| 우클릭 / `Esc` | 건설 모드 및 선택 해제 |
| `Space` | 다음 웨이브 조기 소환 |
| `U` / `X` / `T` | 선택 타워 업그레이드 / 판매 / 타겟팅 변경 |
| `P` | 일시정지 |
| `R` | 스테이지 다시 시작 |
| `Q` | 스테이지 선택 화면으로 |
| 상단 `1x` `2x` `3x` | 배속 |
| 타이틀에서 `1`~`3` | 난이도 선택 · `Enter`/`Space` 시작 |

**결과 화면에서는 다음 행동을 버튼으로 제시한다** — `다음 스테이지 ▶` / `다시 하기` /
`스테이지 선택`. 예전에는 우측 패널 구석의 "다시 시작" 하나뿐이었고 다음 판으로 가는
길은 `Q` 키를 아는 사람만 쓸 수 있었다. 한 판을 깬 직후는 **다음 행동이 화면에 있어야
하는 순간**이라 결과 카드 바로 아래에 놓는다.

## 8. UX 원칙

- **정보를 미리 준다.** 준비 단계에서 다음 웨이브의 구성과 위협 태그(공중/장갑/마저/고속)를
  패널에 항상 표시한다. 상성 게임에서 정보를 숨기면 "시행착오 게임"이 되고 재미가 죽는다.
- **실패 사유를 말한다.** 건설이 막히면 "골드가 40 부족합니다" 같은 구체적 사유를 돌려준다
  (`BuildResult`).
- **적의 방어를 형태로 구분할 수 있다.** 실루엣이 방어 유형을, 날개가 공중 여부를
  나른다. 색은 보조 수단일 뿐이다 — 자세한 규칙은 5장.
- **되돌릴 수 있다.** 판매 70% 환급으로 빌드 실수를 회복할 수 있게 한다.
- **보상은 이름이 아니라 그림과 수치로 보여준다.** 스테이지 클리어 화면의 해금 카드는
  타워 그림 + 한 줄 정체성 + 실제 수치(가격·타입·특수효과) + 왜 필요한가를 함께 싣는다.
  새 기물이 열렸다는 사실보다 **"이걸로 무엇이 달라지는가"** 가 다음 스테이지의 판단을
  바꾸기 때문이다. 이름만 작게 적던 시절에는 해금이 그냥 지나갔다.
- **버튼의 그림과 클릭 영역은 한 곳에서 만든다.** 결과 화면 버튼도 Renderer가 아니라
  `Hud`가 그린다 — 히트 영역을 만드는 쪽이 그리기도 해야 둘이 어긋날 수 없다.
  대신 Renderer가 카드 묶음의 아래쪽 y를 돌려주어 버튼이 카드를 덮지 않게 한다
  (양쪽에서 같은 산수를 따로 했더니 실제로 겹쳤다).

## 9. 밸런스 검증 상태

전체 결과와 방법론은 [`BALANCE.md`](BALANCE.md)에 있다. 요약:

| 질문 | 답 |
|---|---|
| 각 스테이지가 그때 가진 기물로 풀리는가? | **풀린다.** 조합 빌드 S2~S5 전부 100% 클리어 |
| 몰빵 빌드는 막히는가? | **막힌다.** S2 이후 전부 0% (S5는 최종 웨이브에서 저지) |
| 해금이 실제로 필요한가? | **S4에서 확인됨** — 금줄 솟대 0기 0% vs 1기 100%. S5 팥 항아리는 **미검증** |
| 보스가 밸런스를 깨뜨리는가? | 아니다. 1,300판 재검증에서 몰빵 차단·해금 필요성이 모두 유지됨 (S4 서낭당 몰빵만 10%로 새어 나감) |
| 어려움(125%)이 클리어 가능한가? | **조기 소환을 챙기는 빌드만** 가능 (S5 60%). 일반 빌드는 S2부터 무너진다 |
| 경로 수가 난이도에 영향을 주는가? | **크게 준다.** 2·3갈래 맵은 압박을 절반 이하로 낮춰야 같은 체감 |
| 조기 소환 2G/초가 과한가? | 아니다. 클리어 여부를 뒤집지 않고 남은 생명만 올린다 |
| 금줄 솟대가 픽되는가? | **필수다** (S4). 다만 2기 이상은 이득이 줄어든다 |
| 업그레이드가 신규 건설과 경쟁되는가? | 아니다. "키우기"(6기 만렙)는 S2 25% / S4 0% |
