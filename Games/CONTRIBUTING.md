# 게임을 만드는 방법

이 저장소에서 게임은 심심할 때 하나씩 늘어난다. 그때마다 백지에서 시작하면
앞 게임에서 배운 것이 그 게임 폴더에 갇힌다. 이 문서는 **배운 것을 다음 게임이
공짜로 물려받게** 하려고 있다.

물려받을 것이 무엇인지는 분명하다. 조선 방어전에서 밸런스가 세 번 무너졌는데
**셋 다 코드 리뷰로는 안 보였고 셋 다 헤드리스 시뮬레이터가 잡았다.**
(`joseon-defense/src/sim/gate.ts` 맨 위) 그래서 이 문서의 규약은 대부분
"판단을 사람의 눈에서 실행 가능한 것으로 옮긴다"는 한 가지 이야기다.

---

## 1. 등급 — T1 스케치와 T2 작품

**모든 게임에 문서와 시뮬레이터를 요구하면 심심해서 만드는 게임은 안 만들어진다.**
그래서 등급을 둔다.

| | T1 스케치 | T2 작품 |
|---|---|---|
| 규모 | HTML 한 장 정도 | 빌드가 있고 계속 손댈 것 |
| GDD | 한 문단 | 전체 |
| 헤드리스 시뮬 | 없음 | **의무** |
| 밸런스 게이트 | 없음 | **의무** |
| 조작 훅 | 없음 (대개 DOM) | **의무** |
| 참여 역할 | designer(약식) · builder · playtester | 다섯 전부 |
| `verify.yml` | 검증할 게 있으면 | 의무 |

`casino-learning-game`이 T1, `joseon-defense`가 T2다.

**승격은 "이거 계속 만지고 싶다" 싶을 때** 한다. 강등도 있다 — 손 안 대게 된
게임을 T2로 두면 게이트만 CI에서 계속 돈다.

등급은 GDD에 적고, 바꿀 때는 이유를 함께 적는다.

## 2. 역할과 소유권

에이전트 정의는 `.claude/agents/` 아래에 있다.

| 역할 | 쓰는 것 | 못 건드리는 것 |
|---|---|---|
| `game-designer` | `docs/GDD.md` · `docs/ROADMAP.md` | 코드 전부 |
| `game-builder` | 게임 코드 · `src/sim/headless.ts` · 조작 훅 | **`src/sim/gate.ts`** · 평가 문서 · 배포 배선 |
| `balance-analyst` | `docs/BALANCE.md` · **`src/sim/gate.ts`** | 게임 로직 |
| `playtester` | `docs/PLAYTEST.md` | 코드 전부 · **GDD를 읽는 것** |
| `shipper` | `deploy.yml` · `verify.yml` · `site/index.html` · README 표 | 게임 내용 |

**이 표의 오른쪽 칸이 설계의 전부다.** 역할을 나누는 이유는 일을 쪼개는 것이
아니라 이해 상충을 끊는 것이다.

- **builder가 게이트를 고칠 수 있으면 게이트는 없는 것과 같다.** 판정받는 쪽이
  판정 기준을 소유하면 빨간불은 언제나 기준을 옮겨서 꺼진다.
- **playtester가 GDD를 읽으면 "의도대로 동작하네요"만 나온다.** 그건 builder가
  이미 확인했다. 모르는 사람에게 이 게임이 무엇으로 보이는지는 한 번 오염되면
  그 회차에서 복구되지 않는다.

## 3. 산출물의 자리

에이전트끼리는 말로 넘기지 않는다. 서브에이전트는 컨텍스트가 끊기므로
**파일 자리를 고정한다.**

```
Games/<game>/
├─ docs/
│   ├─ GDD.md         designer   → 무엇을·왜. 재미 가설. 등급
│   ├─ BALANCE.md     analyst    → 숫자와 판단 (회차 누적)
│   ├─ PLAYTEST.md    playtester → 블라인드 플레이 기록 (회차 누적)
│   └─ ROADMAP.md     designer   → 회차별 처방 (누적)
└─ src/sim/
    ├─ headless.ts    builder    → 렌더링 없이 한 판
    └─ gate.ts        analyst    → 설계 의도가 깨지면 exit 1
```

`joseon-defense`가 이미 이 모양이다. 새 규칙이 아니라 이름을 붙인 것이다.

### 회차는 덮어쓰지 않고 쌓는다

`BALANCE.md` · `PLAYTEST.md` · `ROADMAP.md`는 append 한다. 각 회차는 날짜와 커밋
해시로 시작한다.

```markdown
## 2026-08-16 · 2da93b6 · 3회차
```

**같은 지적이 세 번 반복되면 그게 진짜 문제라는 신호다.** 한 회차의 인상은
신호가 약하고, 그 신호는 기록이 쌓여야만 보인다. 곡선이 어느 쪽으로 움직이는지가
한 회차의 절대값보다 중요하다.

### 판정 없는 리포트는 실패로 친다

평가 역할은 방치하면 "전반적으로 완성도가 높습니다"를 쓴다. `gate.ts`가
밸런스에 대해 하는 일을 평가 문서에도 강제한다 — **모든 회차는 한 줄 판정으로
시작한다.**

- balance-analyst: `판정: 통과 / 통과 못 함 — <숫자와 경계>`
- playtester: `판정: 다시 함 / 다시 안 함 — <그렇게 만든 사건>`

playtester의 판정이 "좋다/나쁘다"가 아니라 **"다시 할 것인가"**인 것은 의도적이다.
게임에 대해 물을 수 있는 유일하게 의미 있는 질문이라서다.

## 4. 표준 계약 — T2 작품이 지킬 두 가지

게임마다 인터페이스가 다르면 평가 역할이 게임마다 새로 배운다. 딱 두 개만
고정하면 어느 게임에나 그대로 붙는다. 하나는 **숫자로 보는 눈**이고 하나는
**손**이다.

### 4.1 헤드리스 시뮬레이터 — 눈

```bash
npm run sim -- --json    # → { runs: [{ stage, strategy, seed, outcome, ...metrics }] }
npm run balance          # → 게이트. 설계 의도가 깨지면 exit 1
```

- **브라우저와 같은 게임 클래스를 렌더링만 빼고 굴린다.** 따로 구현한 시뮬은
  게임이 아니라 시뮬을 검증하게 된다.
- **시드를 고정해 결정적으로 만든다.** 같은 명령이면 같은 숫자가 나와야
  통계적 여유가 아니라 경계값으로 검사할 수 있다.
- **대조 실험 구조로 짠다.** 다른 조건을 전부 고정하고 축 하나만 바꿔야 결과
  차이를 그 축 탓으로 돌릴 수 있다.

`joseon-defense/src/sim/`의 **코드 짜임**을 참고해도 된다. 스테이지·전략·지표
구성은 그 게임의 장르에서 온 것이라 가져오지 않는다 (6장).

### 4.2 조작 훅 — 손

Canvas에 UI까지 그리는 게임은 DOM 셀렉터가 없어서 playtester가 붙을 자리가 없다.

```js
window.__playtest = {
  ready: Promise<void>,                          // 에셋 로딩·초기화 끝
  state: () => ({ ... }),                        // 지금 무슨 상황인가 (직렬화 가능한 값만)
  hotspots: () => [{ id, rect: {x,y,w,h}, label, enabled }],
}
```

- `label`은 **화면에 보이는 그대로**. `tower_archer_lv2`가 아니라 `궁수 2단계`.
  playtester는 이 문자열로 게임을 읽는다.
- `enabled: false`인 것도 **남긴다.** 눌러도 안 되는 것을 지워버리면 "왜 안
  눌리는지 모르겠다"는 증상을 못 잡는다.
- **프로덕션 빌드에서 빼지 않는다.** 배포본을 그대로 검증할 수 있어야 한다.

같은 훅이 스모크 테스트에도 쓰인다. 예전에 `.smoke.mjs`를 만들었다 버린 자리가
여기다 — 이제 상주할 자리가 생겼다.

## 5. 루프

```
                     아이디어
                        │
                   game-designer          docs/GDD.md
                        │
                 ┌──[ 사람: 만들까? ]
                 │      │
                 │  game-builder ◀────────────────┐
                 │      │                         │
                 │  ┌───┴────┐  ← 병렬. 서로의 결과를 보면 안 된다
                 │  │        │                    │
                 │ balance  playtester            │
                 │  │        │                    │
                 │  └───┬────┘                    │
                 │      │                         │
                 │ [ 사람: 무엇이 문제인가 ]       │
                 │      │                         │
                 │  game-designer ────────────────┘
                 │      │            docs/ROADMAP.md 처방
                 │      │
                 └──▶ shipper  (충분히 됐다 싶을 때)
```

### 사람이 서는 두 자리

**GDD 한 장은 싸고, 만든 다음 "이거 아닌데"는 비싸다.** 그래서 만들기 전에 한 번
선다.

두 번째 자리가 더 중요하다. **평가 결과가 builder로 곧바로 가지 않는다.**

평가는 증상을 말하고, 처방은 설계 판단이다. "3분 지점에서 왜 지는지 모르겠다"는
증상이고, 처방은 (a) 튜토리얼 (b) 난이도 완화 (c) 피해 피드백 UI — **셋 다 다른
게임이 된다.** 그걸 builder가 고르면 게임이 회차마다 조금씩 다른 방향으로
표류하고, 몇 회차 뒤에는 아무도 이게 무슨 게임이었는지 모르게 된다.

그래서 순서는 **평가 → 사람과 논의 → designer가 처방 → builder가 구현**이다.
designer는 처방과 함께 **하지 않기로 한 것**을 적는다. 그게 다음 회차에서 같은
논의를 반복하지 않게 막는다.

### 평가 둘은 반드시 병렬로

balance-analyst와 playtester는 서로의 결과를 보면 안 된다. 숫자를 먼저 본
playtester는 그 숫자를 확인하러 가고, 플레이 인상을 먼저 본 analyst는 그 인상에
맞는 지표를 찾는다. 독립적인 두 관측이어야 서로를 검증한다.

T1 스케치는 designer(약식) → builder → playtester로 짧게 돈다.

## 6. 게임끼리 섞이지 않는다

**게임은 각자 하나의 세계다.** 이 저장소가 갈래별로 폴더를 나누듯, 한 게임을
만드는 동안 다른 게임은 없는 것으로 친다.

지켜야 할 이유가 막연한 원칙이 아니라 구체적이다. 앞선 게임의 문서에는 **그
게임의 장르에서만 뜻이 있는 숫자와 가정**이 들어 있다 — 클리어율 목표 구간,
시드 개수, 대조군 구성, 웨이브라는 개념 자체. 읽으면 딸려 온다. 퍼즐 게임을
기획하러 갔다가 웨이브와 업그레이드를 생각하고 있게 되고, 퍼즐 게임의 밸런스를
"클리어율 40~70%"로 판정하게 된다. **그 회차는 통째로 버린다.**

내버려 두면 이 저장소는 조용히 「타워디펜스 저장소」로 굳는다. 아무도 그렇게
결정하지 않았는데도 그렇게 된다.

### 읽어도 되는 것과 안 되는 것

| | 다른 게임에서 |
|---|---|
| `docs/` 아래 전부 (GDD·BALANCE·PLAYTEST·ROADMAP) | **금지** |
| `src/sim/`의 **코드 짜임** | 허용 — 단 스테이지·전략·지표 구성은 가져오지 않는다 |
| 배포 배선 (`deploy.yml` 등) | 허용 — 저장소 사실이지 게임 내용이 아니다 |
| 이 문서 | 허용 |

`playtester`는 예외 없이 전부 금지다. 자기 게임의 `PLAYTEST.md` 지난 회차만
본다.

형식이 궁금해서 남의 문서를 여는 것도 금지다. 형식은 각 역할 정의에 적혀 있고,
**형식을 보러 갔다가 내용을 배워 오는 것**이 정확히 이 규칙이 막으려는 일이다.

### 세션도 섞지 않는다

**한 세션에 한 게임.** 서브에이전트는 컨텍스트가 깨끗하게 시작하지만,
**그 에이전트에게 써 주는 프롬프트는 깨끗하지 않다.** 앞 게임의 장르·수치·
해결책이 지시문에 묻어 들어가고, 그건 에이전트 쪽에서 막을 방법이 없다.
"조선 방어전처럼 웨이브 구조로" 같은 한마디가 이 게임이 아직 정하지 않은 것을
정해 버린다.

게임을 바꿀 때는 세션을 새로 연다.

### 섞어도 되는 것 — 규약

물려받는 것은 **방법**이지 내용이 아니다. 헤드리스 시뮬레이터로 판정한다는
것, 판정 없는 리포트는 실패로 친다는 것, 회차를 쌓는다는 것 — 이 문서에 적힌
것들은 장르와 무관하므로 전부 물려받는다. 그러라고 이 문서가 있다.

**구분은 간단하다. 이 문서에 있으면 물려받고, 특정 게임 폴더에 있으면
그 게임의 것이다.**

## 7. 프로젝트를 추가할 때 배선 다섯 군데

`shipper`가 처리하지만, 손으로 할 때를 위해 적어 둔다.

1. `.github/workflows/deploy.yml` 「배포 트리 조립」 — 한 줄 (빌드가 있으면 빌드 단계도)
2. `.github/workflows/verify.yml` — T2면 타입 검사 · 빌드 · `npm run balance`
3. `site/index.html` — 카드 한 장
4. `Games/README.md` — 표에 한 줄
5. 루트 `README.md` — 프로젝트 표와 「배포」 주소 표에 각각 한 줄

**주소는 저장소 구조를 그대로 따라간다.** `Games/<name>/` →
`/playground/<name>/`. vite는 `base: './'`로 두어 상대 경로를 쓰게 한다.
